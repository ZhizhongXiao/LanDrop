## 1. 项目目标

开发一个以 Python 局域网 HTTP 服务为核心的 Windows 小工具，让服务机与客户机在可信的局域网中方便地传输文件。首要支持家庭 `Private` 网络和用户自有手机热点；不以陌生 `Public` 网络作为运行场景。

本文统一使用以下角色名称：**服务机**是运行 LanDrop 的 Windows 电脑；**客户机**是通过浏览器连接的手机或另一台电脑；**服务端/客户端**用于描述软件与 HTTP 通信角色。历史实测记录中的“手机”或“PC”保留其真实测试设备含义。

最终希望具备以下使用流程：

1. 在服务机上选择共享目录和接收目录。
2. 点击“开启传输”。
3. 程序显示访问地址和二维码。
4. 客户机通过浏览器访问，从服务机下载文件或向服务机上传文件。
5. 服务默认运行 5 分钟。
6. 即将到期时，Windows 通知允许“重置为 5 分钟”或“立即关闭”。
7. GUI 窗口关闭后隐藏到系统托盘，需要时可以重新打开。
8. 服务到期后关闭监听端口，托盘程序继续等待下一次启动。

这个项目首先服务于开发者本人，不以立即发布成熟商业软件为目标。

## 2. 开发原则

### 2.1 一次只解决一层问题

先确认文件传输链路可用，再加入上传、GUI、托盘、通知以及网络与防火墙诊断。不得在核心功能尚未稳定时同时堆叠所有功能。

### 2.2 每个阶段都必须可以独立运行和验收

每完成一个阶段，都要保留一个可运行版本。后续功能出现故障时，可以回到前一阶段定位问题。

从第七阶段起，验收分为两层：

- **阶段开发验收**：本阶段功能、自动化、本机实机与已具备条件下的关键回归达到冻结标准后，可以作为下一阶段开发基线；
- **最终发布验收**：跨机器、无开发环境、安装/升级/卸载和系统状态恢复等发布门槛全部完成后，才允许宣称版本可正式发布。

若某个发布门槛仅因测试环境暂不可用而延期，必须明确记录延期项、已有证据和补测条件；不得把“允许进入下一阶段开发”写成“最终发布验收完成”。

### 2.3 可信专用网络优先

程序仅面向用户信任的 `Private` 网络运行，主要场景包括家庭 Wi-Fi 和用户自有手机热点。`Public` 网络不作为后期高级功能，而是明确列入本项目的不支持范围。若服务机当前连接被 Windows 标记为 `Public`，程序不启动文件传输服务，只解释原因并提供 Windows 设置入口。

### 2.4 安全边界优先于功能数量

程序只能访问用户明确选择的目录。不得因为方便而开放整个磁盘、任意系统路径或远程命令执行能力。

### 2.5 重要状态必须在界面中说清楚

不使用含义模糊的“已连接”。应分别显示服务器状态、监听地址、网络类型、防火墙状态、剩余时间和正在传输的文件。

### 2.6 面向初学者保留实验记录

遇到问题时先记录现象、测试条件和结果，再修改代码。每次只改变一个主要变量，避免不知道究竟是哪项修改解决了问题。

### 2.7 系统网络配置只检测、不代改

程序只读取 Windows 当前网络类别、防火墙状态、活动网卡和 IPv4，并在需要时打开对应的 Windows 官方设置入口。程序不自动把 `Public` 改成 `Private`，不自动关闭防火墙，也不以管理员权限替用户修改防火墙规则。用户完成系统设置后，由程序重新检测实际状态。

### 2.8 轻量化优先，不为理论风险堆叠体系

项目定位是把 `python -m http.server [端口]` 式的临时局域网传输体验做得更顺手，而不是重新实现 SMB、就近共享或企业级文件传输平台。安全设计以“避免误操作、限制暴露范围、可信 Private 网络内可用”为目标，不引入账号体系、复杂权限模型、证书基础设施或大量高级配置。

第一阶段继续使用 `python -m http.server` 或标准库等价实现作为最小链路验证工具，用于确认 LAN 可达性、监听地址、下载行为和网络诊断基线。

从第二阶段开始，正式 HTTP 应用层优先采用 **Bottle**。选择 Bottle 的原因是：它保持单文件、轻量、无额外第三方依赖链的特性，同时直接提供路由、文件上传、Cookie、静态文件服务等能力，可以避免手写 `BaseHTTPRequestHandler` 时反复处理 Cookie、multipart 上传、路径安全和 URL 分派等细节。除非后续需求明显超出 Bottle 的能力，否则不再把 Flask/FastAPI 作为当前路线。

### 2.9 网络环境变化不做热迁移

程序每次启动服务时重新检测当前活动局域网、IPv4 和网络类别，不保存固定 LAN IP。若服务运行期间发生 Wi-Fi 切换、热点切换、IPv4 变化或活动网卡变化，当前会话直接终止，旧地址和二维码失效；用户重新点击“开启传输”后重新检测并启动。项目不开发跨网卡热迁移。

## 3. 已确定的产品边界

### 3.1 已确定内容

- 开发语言使用 Python。
- 目标系统首先是 Windows 11。
- 手机端首先使用浏览器，不开发 Android App。
- 桌面 GUI 已采用 pywebview，本地 HTML/CSS/JavaScript 已从 Python 控制层拆分到 `ui/desktop/`。
- 程序采用“需要时开启，不用时关闭”的临时服务模式。
- 单次服务默认维持 5 分钟。
- GUI 可以隐藏到 Windows 系统托盘。
- 即将到期时使用 Windows 通知提醒关闭或将倒计时重置为 5 分钟。
- 支持可信 `Private` 网络，主要包括家庭 Wi-Fi 和用户自有手机热点。
- 多网络采用“每次启动重新检测”的方式适配，不保存固定 IPv4；家庭 Wi-Fi 与手机热点可获得不同地址。
- 服务运行期间若网络或 IPv4 变化，终止当前会话并要求重新开启服务。
- 不支持在 `Public` 网络中启动文件传输服务。
- Windows 网络类别和防火墙配置只检测并提供设置入口，不由程序自动修改。
- 第七阶段已完成 `--onedir` 主程序工程与便携回归；第八阶段正式实现安装器、卸载器与分发。
- 第八阶段正式安装采用当前用户范围：程序根固定为 `%LOCALAPPDATA%\Programs\LanDrop`，用户数据继续位于 `%LOCALAPPDATA%\LanDrop`。
- 正式安装后的主程序采用 PyInstaller `--onedir`；单文件 `Setup.exe` 和单文件 `Uninstall.exe` 采用 PyInstaller `--onefile --windowed`。
- Setup、LanDrop、Uninstall 均不主动创建、修改或删除 Windows 防火墙规则，也不修改网络类别；系统授权由 Windows 与用户决定。
- Microsoft Edge WebView2 Runtime 作为外部运行前置条件，不随 LanDrop 打包、不由安装器联网下载；发布说明明确声明，程序仅做本地检测。
- 防火墙必须保持开启；正式方案不能依赖关闭防火墙。

### 3.2 不实现或当前不实现的内容

以下内容分为两类：`Public` 网络支持属于明确不实现的产品边界；其余项目在当前版本不实现，除非后续需求发生变化。

- **不实现：在 Windows `Public` 网络中提供文件传输服务。**
- 公网访问和端口映射。
- 手机 MAC 地址鉴权。
- 面向陌生网络的完整 HTTPS 证书与信任体系。
- Windows、Android 原生双端应用。
- 多用户账号系统。
- 高并发传输。
- 云端中转。
- 自动更新。

### 3.3 为什么不开发 Public 网络模式

`Public` 网络不是简单地在现有服务上增加一个“允许公用网络”开关。若要在咖啡店、酒店、机场、公司访客网络等陌生局域网中可靠传输文件，至少会引入以下额外成本：

- **客户端认证**：同一网络中可能存在未知设备，必须可靠区分已信任客户端与陌生客户端，不能依赖 IP 或随机 MAC。
- **传输加密**：普通 HTTP 会暴露文件内容和访问凭据；面向不可信网络需要 TLS/HTTPS 或等价的安全传输机制。
- **证书信任**：局域网 IP 很难直接获得浏览器天然信任的证书。自签名证书虽然能加密链路，但浏览器无法天然确认服务器身份；若建立自有 CA、安装证书或引入域名，会显著增加部署和维护成本。
- **中间人、窃听与重放风险**：仅增加配对码或 Cookie 不能自动解决不可信网络中的中间人攻击、凭据窃取和重放问题。
- **网络环境差异**：公共 Wi-Fi 可能启用客户端隔离、访客网络策略、端口限制、企业组策略或第三方安全软件，程序无法保证设备间能够直接通信。
- **测试矩阵扩大**：需要额外覆盖酒店/咖啡店/公司网络、不同路由器隔离策略、证书异常、认证失败、HTTPS 浏览器兼容等大量场景。
- **长期维护成本**：一旦宣称支持 Public 网络，就需要长期维护认证、加密、证书、兼容性和安全问题，这与本项目“临时、轻量、个人使用优先”的目标不符。

因此，本项目明确不开发 `Public` 网络传输能力。外出使用时，优先建议使用用户自己的手机热点，并将该连接在 Windows 中作为可信 `Private` 网络使用。程序仍会识别 `Public` 网络，以便说明为什么不能启动服务并提供 Windows 设置入口；这属于诊断功能，不代表支持 Public 网络。

### 3.4 HTTP 服务实现边界

- 第一阶段以 `python -m http.server` 或标准库等价实现作为轻量原型，验证 LAN 链路、地址展示、监听状态和基本下载。
- 从第二阶段起，正式 HTTP 应用层采用 **Bottle** 作为首选实现。
- 选择 Bottle 的主要原因：
  - 单文件框架，整体足够轻量；
  - 无额外第三方依赖链，便于源码运行和后续便携打包；
  - 原生提供路由、请求/响应封装、Cookie、文件上传和静态文件服务；
  - 能显著降低手写 `http.server` Handler 时对 multipart、Cookie、URL 分派和路径安全的维护成本；
  - 能力与本项目“Private LAN + 浏览器客户端 + 临时服务 + 少量接口”的规模匹配，不需要引入 Flask/FastAPI 的更大功能面。
- `python -m http.server` 继续保留为网络基线、故障排查和只读原型工具，不作为最终双向传输实现。
- 若后续需求明显超出 Bottle 能力，再单独重新评估更完整的框架；当前不提前为理论扩展预留大型 Web 架构。

### 3.5 客户端信任模型（已实现）

Private 网络不能替代客户端身份识别，但本项目也不采用 IP 或 MAC 作为长期设备身份。当前采用“配对一次、后续自动识别”的轻量模型：

- 手机端继续使用浏览器，不开发专用 Android App。二维码只是把浏览器带到当前服务 URL 或一次性配对 URL。
- 第一次由用户完成配对/确认；成功后浏览器保存高熵随机凭据，PC 端保存相应凭据哈希或等价不可逆记录。
- 后续再次访问时浏览器自动携带凭据，不要求用户反复输入配对码。
- DHCP 地址、SSID、随机 MAC 和当前 IP 不作为长期客户端身份。
- 用户可以在 PC 端取消信任；浏览器清除站点数据、无痕模式或重装浏览器后需要重新配对。
- 该模型只面向可信 `Private` 网络，不宣称达到陌生 Public 网络下的认证与抗窃听安全等级。

### 3.6 尚未最终确定的技术选择

以下内容不属于第八阶段当前阻塞项，后续有明确需求时再评估：

- 完整可靠的大文件上传续传方案；当前 `.part` 仅用于事务安全，不是续传状态。
- 下载虽然已支持标准 HTTP Range，但浏览器是否自动续传仍取决于浏览器下载管理器。
- 是否在正式安装包之外另行提供免安装的单 EXE `--onefile` Portable 构建；当前第八阶段不以此为硬门槛。

第八阶段正式分发形态已经冻结：安装后的主程序继续使用 `--onedir`，安装器和卸载器使用 `--onefile --windowed`。

## 4. 需要逐步理解的五个通信概念

| 概念 | 当前阶段够用的理解 |
| --- | --- |
| IP 地址 | 服务机在当前局域网中的门牌号，例如 `192.168.1.35` |
| 端口 | 某个程序使用的网络入口；LanDrop 固定使用 TCP `8000` |
| 监听 | 程序打开端口并等待其他设备访问 |
| HTTP 请求 | 客户机浏览器向服务端请求网页或文件 |
| 防火墙 | 决定外部设备是否允许进入这个端口 |

暂时不要求系统学习 TCP、路由、DNS、TLS、子网划分等完整理论。实际遇到相关问题时再补充对应知识。

## 6. 第一阶段：家庭网络只读下载原型

本章保留第一阶段启动时的实施方案与开发机调查历史基线；其中“当前尚未完成”“仍需确认”等语态指当时状态，不是 V4 当前待办。第一阶段最终完成情况以本章实施状态、后续阶段记录和测试日志为准。

### 6.1 阶段目标

在可信家庭 Wi-Fi 中，由服务机启动一个只读文件服务器，客户机通过浏览器访问并下载指定目录内的文件。服务器可以手动关闭，且关闭后端口不再接受访问。

这一阶段不开发完整 GUI，不做上传，不自动修改网络类别或防火墙。若检测到 `Public` 网络，只记录并验证“拒绝启动 + 给出说明”的行为，不进行 Public 网络传输测试。

### 6.2 使用条件

- 电脑运行 Windows 11。
- 电脑与手机处于同一个可信局域网，优先使用家庭 Wi-Fi；也可以测试用户自有手机热点。
- Windows 将当前连接设置为 `Private`。
- Windows 防火墙保持开启。
- 当前 Python 环境可正常运行脚本。
- 测试时明确记录 Clash、VPN 或 TUN 是否开启。

### 6.2.1 已确认的开发机网络基线（2026-09-14）

当前已在“电脑连接用户自有手机热点”的环境下完成一轮基线检查：

- 当前实际 LAN 接口为 `WLAN`。
- 当前热点 IPv4：`10.118.84.152`。
- 子网掩码：`255.255.255.0`，即当前 IPv4 网段可按 `/24` 理解。
- IPv4 默认网关：`10.118.84.206`。
- 同时可见一个 IPv6 链路本地网关地址；首版仍只使用 IPv4，不把 IPv6 纳入地址展示和绑定策略。
- Windows 将当前热点连接识别为 `Private`。
- `Meta` 为当前代理软件使用的 TUN 虚拟适配器，不作为文件服务器 LAN 地址候选。
- `无线局域网适配器 本地连接* 1`、`本地连接* 2` 当前均为断开状态，不作为当前 LAN 接口；后续按 Wi-Fi Direct/虚拟接口处理。
- `以太网适配器 蓝牙网络连接` 不属于当前目标传输路径，默认排除。
- 当前代理/VPN 使用“规则（Rule）”模式。程序不控制代理模式，只把 TUN/VPN 作为诊断因素；局域网访问应由代理配置放行直连。
- 当前 Windows 防火墙界面可见：`Python HTTP 8000` 允许 `Private`；另有两个同名 `Python` 项，分别存在 `Private` 与 `Public` 勾选；`PowerShell` 同时允许 `Private/Public`。这些显示项尚未核对到具体 `python.exe` 路径、协议和端口，因此不能仅凭名称判断哪条规则实际控制当前服务器。
- **历史记录：**第一阶段启动时曾在 `8765` 与 `8000` 间待选；后续实现、测试命令和防火墙诊断对象已经统一固定为 TCP `8000`。

第一阶段启动时尚未完成的开发机侧核验（历史记录）：

1. 当前实际使用的 `python.exe` 路径，与防火墙中两个 `Python` 项分别对应哪个可执行文件。
2. 运行 `http.server` 时实际 `LocalAddress` 是 `0.0.0.0`、WLAN IPv4 还是其他地址。
3. 热点网段 `10.118.84.0/24` 的 Windows 本地路由是否明确落在 `WLAN`，以及 `Meta` TUN 对该网段是否存在异常捕获。
4. 家庭 Wi-Fi 在当前配置下尚未完成同一套基线复测。

有线 Ethernet 不列为首版开发机验收条件：当前笔记本没有原生 RJ45 端口，也没有必要为了首版专门建立有线测试环境。代码不应主动排斥 Ethernet，但首版正式验证以 Wi-Fi LAN 为主。

10. 路由器/热点是否启用了访客网络、AP Isolation 或客户端隔离。
11. 是否存在第三方防火墙或终端安全软件额外阻止入站连接。

## 7. 后续阶段的初步边界

### 第二阶段：安全上传与文件处理

从本阶段开始，正式 HTTP 应用层切换为 **Bottle**。Bottle 负责路由、浏览器文件上传、Cookie 读写和静态/下载响应；文件路径校验、`.part`、同名策略、磁盘空间检查和流式写入仍由项目自身的文件处理模块负责。

重点处理固定接收目录、文件名清理、同名文件、临时 `.part` 文件、大小限制、磁盘空间和流式上传。完成后形成可双向传输的命令行版本。

当双向传输链路稳定后，再加入轻量的“首次配对—长期信任”机制：首次由用户确认，后续浏览器凭据自动识别可信客户机；不使用 IP/MAC 白名单，不要求每次重新认证。该认证只面向 Private 网络，浏览器凭据由 Bottle 的 Cookie 能力承载，服务机保存相应凭据哈希或等价不可逆记录。

### 第三阶段：桌面 GUI

使用 pywebview 建立控制窗口，将服务器逻辑与界面逻辑分离。界面负责选择目录、启停服务、显示地址与状态，不直接承担文件传输。

实施状态（2026-09-15）：已完成并通过人工验收。桌面入口为 `desktop.py`；控制窗口支持原生目录选择、上传上限设置、非阻塞启停、访问地址、网络接口和配对码显示，以及使用系统浏览器打开传输页。文件传输仍由 Bottle 应用处理。服务控制器具备重复启动保护和线程安全的幂等关闭；在第三、四阶段，GUI 停止服务或直接关闭窗口后，TCP 8000 均已验证释放。该“关闭窗口即停止”语义是阶段历史行为，已在第五阶段替换为隐藏到托盘。命令行入口 `app.py` 保持兼容。

### 第四阶段：5 分钟生命周期

使用会话 ID 和单一截止时间管理倒计时。到期后拒绝新传输，并为已经开始的传输提供有限宽限。旧计时器和旧通知不得控制新会话。

实施约定（2026-09-16）：默认会话 5 分钟；点击“重置为 5 分钟”会从点击时重新计算完整 5 分钟，而不是在原截止时间上累加；剩余 60 秒进入醒目提示。截止时间在监听器准备完成后开始计算，避免初始化耗时侵占可用时间。到期立即拒绝新请求，已开始的上传和下载最多宽限 60 秒。手动停止立即生效。检测到睡眠恢复后终止会话，不暂停倒计时。配对码对每台新设备单次有效，配对成功后原子轮换；已有可信客户机不消耗配对码。传输量与速率使用十进制 `MB / MB/s`。同一次文件下载的并行 HTTP Range 请求按逻辑任务和字节区间聚合，文件任务与请求流分别计数，重叠字节不重复计入主传输量。服务停止原因与传输失败原因分别统计，并写入不包含路径、配对码或凭据的本地轮转日志。

正式设备管理由 PC 控制窗口负责，可列出并撤销单个或全部可信浏览器；手机端仍可自助取消自身信任。文件链接先进入手机状态页，再在隐藏下载目标中启动附件响应。连接中断后状态页保留明确提示；服务重新启动且文件未变化时，服务器支持标准 HTTP Range 请求，浏览器是否自动继续由具体下载管理器决定。

### 第五阶段：托盘与 Windows 通知

关闭 GUI 只隐藏窗口；退出应用才终止托盘进程。通知提供“重置为 5 分钟”“立即关闭”和“打开窗口”。主程序保持普通权限运行。

实施状态（2026-09-17）：已完成并通过人工与自动化验收。`pystray` 提供最小托盘入口，`Windows-Toasts` 提供到期提醒和自动关闭通知，`ActionCoordinator` 统一承接 GUI、托盘与 Toast 动作，`ServiceController` 仍是服务状态的唯一权威。活动传输中点击 X 后窗口隐藏、传输继续且 TCP 8000 保持监听；同一窗口连续恢复 20 次未丢失状态。托盘重置、停止、退出，Toast 重置、停止、打开窗口，旧 revision/session 隔离，通知清理失败兜底，托盘初始化失败保护及异常退出遗留通知清理均已通过。最终 Private 热点实测启动约 `0.396s`、停止约 `0.173s`；第五阶段收官时共有 43 项自动化测试。

已知非阻塞系统行为：Windows 已展开的托盘菜单不会在后台状态变化时原地重绘，收起后重新打开即可读取最新状态；Windows 前台保护下窗口激活只保证尽力而为，但窗口可靠可见和状态不丢失已经通过验收。源码开发机已注册自定义 AUMID `LanDrop.Desktop`；后续便携打包与安装阶段必须验证目标机上的 AUMID、快捷方式和通知身份注册策略。

#### 第五阶段冻结方案（2026-09-16）

第五阶段的技术选型和职责边界在正式编码前冻结。托盘的核心任务仅是：在主窗口隐藏后仍可找回窗口，并控制已经运行的服务。它是 GUI 的一个入口，不是第二个 GUI；不实现复杂自定义托盘界面、独立配置页、文件浏览器或第二套状态/计时界面。

组件职责固定如下：

```text
pywebview Window（从程序启动存活到应用退出）
  └─ 主控制窗口：目录、可信客户机、启停与完整状态

pystray Tray
  └─ 托盘图标和简洁菜单

Windows-Toasts
  └─ Toast 投递和按钮动作入口

ActionCoordinator
  ├─ 统一接收 GUI、托盘和 Toast 动作
  ├─ 调度窗口显示/恢复
  └─ 调用 ServiceController 的公开动作

ServiceController（service.py）
  └─ 服务、会话、截止时间、端口与传输生命周期的唯一权威控制器
```

- `pystray` 只负责 Windows 托盘；不因托盘引入 `pywin32`。若先行验证发现 `show()/restore()` 后的前台激活需要补充，只允许通过 pywebview 当前 Windows 原生后端做最小“尽力激活”，不得因此新增第二套窗口控制体系。
- `pywebview` 继续负责唯一主窗口。窗口从应用启动一直存活到应用退出；点击 X 时只隐藏，不销毁并重建 Window。
- `service.py` 中的 `ServiceController` 继续是启停、会话、截止时间、端口和传输生命周期的唯一权威控制器。第五阶段新增 `landrop/tray.py` 作为托盘适配器，并新增统一动作协调层；二者不得复制服务状态机。
- `Windows-Toasts` 独立负责 Windows Toast。交互 Toast 固定使用自定义 AUMID `LanDrop.Desktop`；本项目只保证 LanDrop 进程仍存活时通知中心按钮能回送到当前进程，不实现“进程退出后由旧通知重新启动应用”。应用启动时清理可能由异常退出遗留的 LanDrop 可操作 Toast，正常退出时再次清理当前可操作 Toast。
- 托盘和 Toast 都不直接接触 Bottle、WSGI、socket 或计时器；它们只能调用统一协调层。pystray 与 Windows-Toasts 的回调线程不得直接操作 pywebview Window，所有窗口显示、恢复和激活动作必须经统一 GUI 调度路径执行。

##### 托盘菜单与窗口语义

第五阶段正式托盘菜单保持最小化：

```text
打开窗口
────────────
状态：运行中 / 已停止        （只读）
重置为 5 分钟               （仅服务运行时启用）
停止服务                     （仅服务运行时启用）
────────────
退出 LanDrop
```

托盘不提供“启动服务”、目录选择、可信客户机管理或实时逐秒倒计时；启动服务及完整配置仍回到主窗口完成。服务状态变化时才刷新托盘菜单，不为秒级倒计时每秒更新菜单。

在托盘已确认可用 (`tray_ready`) 时，窗口关闭语义为：

```text
活动传输 → 点击 X → pywebview 窗口隐藏 → 服务继续运行
         → 传输继续 → TCP 8000 继续监听

服务已停止 → 点击 X → 窗口隐藏 → 托盘进程继续等待下一次使用
```

若托盘初始化失败或运行中失效，不允许把主窗口隐藏成无法找回的后台进程。无托盘降级语义固定为：禁用“关闭到托盘”；点击 X 时直接通过统一 `request_exit(reason="app_exit")` 安全退出，并在能够显示状态时提示“托盘不可用，关闭窗口将退出 LanDrop”。不得产生不可找回的隐藏进程。

窗口重新打开时优先使用 `show()`/`restore()`；只有先行技术验证确认焦点不可靠时，才加入最小 Windows 原生“尽力激活”补充。硬性验收是窗口可靠重新可见且状态不丢失；Windows 前台焦点保护导致的偶发未抢到焦点不视为服务失败。

##### Toast 状态安全与生命周期

`ServiceController` 维护当前 `session_id` 和 `deadline_revision`：每次启动服务生成新的 `session_id`；同一服务会话中每次重置截止时间都递增 `deadline_revision`。

修改服务状态的 Toast 动作必须携带创建通知时的 `session_id + deadline_revision`。`reset` 与 `stop` 的“校验当前 session/revision + 执行动作”必须在 `ServiceController` 的同一锁/同一原子控制路径中完成，禁止先校验、后另行调用造成竞态。旧会话或旧 revision 的动作一律安全忽略。

“打开窗口”属于无状态 UI 动作，不修改当前服务，因此不因旧 `session_id/revision` 被拒绝；它只请求显示当前 LanDrop 窗口。

每个 `session_id + deadline_revision` 最多发送一次“即将到期”可操作 Toast。默认正式会话在剩余 60 秒时触发。Toast 使用固定 LanDrop 通知组，并以 `session_id + deadline_revision` 生成可唯一定位的 tag，便于替换和清理。发生重置、停止、会话到期、启动新会话或应用退出时，主动移除已经失效的可操作 Toast；应用启动时也清理异常退出可能遗留的旧可操作 Toast。主动清理只用于保持通知中心整洁，`session_id/revision` 原子校验仍作为最终安全兜底。GUI、托盘和 Toast 发起的普通“停止服务”统一沿用 `manual_stop`；只有应用整体退出使用 `app_exit`。

##### 统一退出

托盘“退出 LanDrop”是正常用户退出入口，但清理逻辑不得写死在托盘模块。所有合法退出路径统一调用 `request_exit(reason=...)`：

```text
标记应用进入 exiting
→ 使后续旧 Toast 状态修改动作失效
→ 通过 ServiceController 停止当前服务和活动传输
→ 清理当前可操作 Toast
→ 停止 pystray
→ 销毁 pywebview Window
→ 退出进程
```

正常用户退出的会话停止原因使用 `app_exit`。第四阶段的 `window_closed` 停止原因和相关验收仅代表第五阶段前的历史行为；第五阶段起点击 X 不再产生该停止原因。单实例/重复启动处理不属于第五阶段阻塞项，留到后续稳定性与打包阶段处理。

### 第六阶段：网络与防火墙诊断

本阶段不扩展传输协议本身，重点是在现有可用链路上增加“启动前建立网络事实、运行中轻量验证、异常时给出可解释诊断”的能力。程序继续只读检测 Windows 网络、防火墙、代理和 VPN/TUN 状态，并提供系统设置入口；不得以管理员权限自动修改网络类别、防火墙规则、代理、VPN、静态 IP 或其他系统策略。

实现进度（2026-09-18）：已完成 session endpoint 冻结、独立轻量 checker、瞬时异常二次确认、明确 Public 立即以 `network_changed` 停服、网络变化自动通知、异步限时深度诊断、分层防火墙证据、显式接口选择和主控/信息/设置三页基础功能。65 项自动化测试通过；原始流上传的超限、错误 CSRF、请求体提前中断、客户端断开分类与清理已有覆盖。原生 IPv4 地址表读取 500 次平均约 `2.68 ms/次`，运行期周期暂定地址 3 秒、NetworkCategory 15 秒、异常二次确认 0.75 秒。深度诊断的网络与防火墙 PowerShell 查询改为后台并行并统一在 10 秒终止；权限不足、查询卡顿或超时时降级为“无法确定”，不进入同步启动硬路径。Private 家庭 WLAN、网络变化、PC↔PC Ethernet、Public 运行期停服与显式 Public 启动拒绝已经通过；Ethernet 分层吞吐、双向 1 GB 完整性和流式上传途中停服均已验收，PC↔PC LAN 必选项完成。无 WAN 路由器、物理拔线、5 GB/并发、SMB 和交换两机角色均为可选补测。

#### 第六阶段冻结方案（2026-09-17）

##### 1. 启动检测权重高，是本次会话的权威网络基线

每次点击“启动服务”时执行一次完整网络检测，并把结果作为本次 session 的网络标准。同步启动硬路径必须明确确认选中 endpoint 为 `Private`；`Public` 或无法确认是 `Private` 时仍然拒绝启动。至少记录：

```text
selected_interface_index
selected_ipv4
network_category
network_profile / 诊断所需标识
防火墙诊断状态 / 快照（允许异步完成）
辅助网络信息
```

`InterfaceIndex` 作为本次进程内 session 的接口身份，接口别名只用于显示，不作为持久身份或安全判断依据。现有 `LanInterface.interface_index` 与 Windows `GetIpAddrTable` 返回的 IPv4/接口索引映射可以直接作为 endpoint 校验基础；服务或应用重启后必须重新完整检测，不跨 session 持久复用 InterfaceIndex 或 IPv4。

启动检测负责“选择并建立本次会话的网络事实”；运行期监测只负责低权重地验证这些事实是否仍成立，不重新选择更优网络、不自动迁移监听器，也不因为后来出现新的 WLAN、Ethernet 或 TUN 接口而切换当前服务。完整防火墙规则扫描不进入同步启动硬路径：改为异步深度诊断或使用短超时，未完成时显示“检测中”，失败时显示“无法确定”。未发现明确 allow 只形成警告，不阻止已经确认安全的 Private endpoint 启动。

##### 2. 运行中网络变化按已选 endpoint 判断

本次 session 的核心 endpoint 定义为：

```text
InterfaceIndex + bound IPv4 + NetworkCategory
```

运行期间遵守以下规则：

- 原 `InterfaceIndex + IPv4` 仍然存在且连接仍为 `Private`：当前服务继续。
- 新增其他 WLAN、Ethernet、TUN/VPN 接口：不影响当前 session。
- 其他非选中接口消失、IP 变化或路由优先级变化：不直接影响当前 session。
- 原选中接口断开/消失：终止当前 session。
- 原绑定 IPv4 从选中接口消失或发生变化：终止当前 session；即使仍连接同一路由器或同一子网，也不尝试热迁移。
- 明确读取到当前选中连接由 `Private` 变为 `Public`：立即以 `network_changed` 终止当前 session，不等待二次确认。
- 不尝试判断多个接口是否属于“同一个实际网络”；只判断当前已绑定 endpoint 是否继续成立。

网络变化后的主 GUI 使用简化提示，例如“网络环境已变化，传输服务已安全停止，请重新开启”。停止原因统一使用 `network_changed`；终端、调试页或诊断日志记录更具体的子类型，例如 `interface_changed`、`address_changed`、`category_changed` 以及旧值/新值。服务停止后由用户重新启动，届时再执行完整检测并建立新的 endpoint。

`network_changed` 属于非人为自动关闭：端口释放后先刷新托盘状态，再发送无动作按钮的“网络变化，服务已安全关闭”通知；点击通知正文只打开当前 GUI，不自动重新启动或迁移服务。该动作复用第五阶段已有的统一协调和通知路径。

##### 3. DNS、SSID、默认网关只作为诊断信息

DNS、SSID、默认网关、路由 metric 等信息可以显示在信息/调试界面并用于排查，但其本身不作为直接停止当前 session 的条件。LanDrop 作为被局域网客户端主动访问的服务端，优先关心当前冻结的 `InterfaceIndex + IPv4 + NetworkCategory` 是否仍有效，而不是 Windows 当前默认互联网出口是否发生变化。

##### 4. 运行期监测保持低频和轻量

不采用“根据机器性能动态调频”的额外状态机。启动时可以记录完整检测耗时作为性能数据，但运行期采用固定低频的轻量 endpoint 检查；具体周期在第六阶段技术验证中通过 `2s / 3s / 5s` 等候选实测后冻结。

运行期不得直接复用现有 `discover_interfaces()`：该函数会通过 PowerShell 执行 `Get-NetConnectionProfile`，完整发现路径明显重于轻量监测。应新增独立 endpoint checker，优先复用 `_read_ipv4_table()` 的原生 IP Helper API，只检查启动时冻结的 `InterfaceIndex + IPv4` 是否仍存在，并以较低频率核验 NetworkCategory；不得重新枚举全部候选、重新选网或扫描防火墙。

若查询失败、暂时为空、接口/地址短暂缺失或出现其他疑似异常，不立即杀死 session；短时间后执行一次快速二次确认，第二次仍不匹配启动基线时才确认 `network_changed`。明确读到 `Public` 是安全边界变化，立即停止，不适用二次确认。第四阶段已有的睡眠恢复路径继续优先使用 `system_resume`，不等待网络确认。

##### 5. 防火墙采用分层诊断，不做绝对化推断

Windows 防火墙规则可能来自精确端口规则、程序规则、较宽泛的 Profile allow、显式 block、组策略或第三方安全软件，因此 GUI 不把复杂规则压缩成一个不可靠的“允许/禁止”结论。

诊断至少区分：

- Windows 防火墙总体/Profile 是否开启；
- 是否发现与 TCP 8000 匹配的精确 Private allow；
- 是否发现当前程序路径对应的 Private allow；
- 是否存在更宽泛的可能允许规则；
- 是否发现与当前场景相关的显式 block；
- 未能从当前可见规则中得出确定结论。

“未发现明确 allow”只显示警告/需检查，不阻止启动。硬性阻止仍以 `Public`、无法可靠选择合法 LAN endpoint 等安全边界为主。程序只提供证据、风险级别和 Windows 官方设置入口，不代替 Windows Filtering Platform 做绝对判定。

##### 6. GUI 规划为主控 / 信息 / 设置三页

正式 GUI 方向冻结为三类页面：

```text
[主控] [信息] [设置]
```

- **主控页**：服务启停、倒计时、下载/上传目录、配对信息、可信客户机等高频功能。
- **信息页**：本次服务绑定的接口和 IPv4、其他可见 LAN、Network Profile / Private-Public、防火墙诊断、TUN/VPN、监听地址，以及服务端/客户端上传下载任务、请求流和速率等运行信息。
- **设置页**：LanDrop 自身重新检测/重试，以及打开 Windows 网络、防火墙、代理等官方设置页面的支持按钮。“测试与调试入口”不是当前功能；如后续确有需要，必须作为新增功能单独设计。后续所谓“恢复”仅指重新检测、刷新状态、重试启动或恢复 LanDrop 自身功能；不得自动修改 Windows 网络、防火墙、代理、VPN 或 IP 配置。

##### 7. TUN/VPN 中性展示

当前实机长期在 VPN + TUN 环境中使用而未发现 LanDrop 传输异常，因此“检测到 TUN/VPN”本身不是警告条件。信息页应列出检测到的虚拟接口/代理相关状态，并明确当前是否被选作 LanDrop LAN；正常情况下应显示为“已检测到，但未被选作 LanDrop LAN”。只有无法可靠识别真实 LAN、TUN 被误选为候选或实际路由/可达性诊断出现异常时才升级为警告。

程序不解析或控制 Clash 等代理软件的业务模式；可以提供打开 Windows“设置 → 网络和 Internet → 代理”等系统入口。

##### 8. Ethernet 纳入第六阶段正式验证

第六阶段不再只以 Wi-Fi 为人工验收范围。Ethernet 测试至少覆盖：

1. **无 WAN 的纯局域网路由器**：路由器不连接互联网，LAN/DHCP 正常工作，两台 Windows 设备通过 LAN 口或 LAN + Wi-Fi 组成纯局域网。
2. **两台 Windows PC 网线直连**：不经过交换机/路由器，双方固定使用 RFC1918 静态地址，例如 `192.168.50.1/24` 与 `192.168.50.2/24`，并由用户确认两端 NetworkCategory 为 `Private`；验证 LanDrop 能正确识别 Ethernet endpoint、绑定 TCP 8000 并完成双向传输，同时保留改为 `Public` 后拒绝启动的反向测试。不依赖 `169.254.0.0/16` 自动链路本地地址，因为当前 `is_lan_ipv4` 明确排除 link-local。
3. **WLAN + Ethernet 共存**：沿用 endpoint 规则；服务只跟踪启动时选中的 `InterfaceIndex + IPv4 + NetworkCategory`。其他接口出现或消失，只要当前 endpoint 仍有效就不终止服务。

PC 直连场景已经有过手动 IP/掩码与稳定发包的先行验证；正式阶段仍需记录具体网卡、链路速率、IP、Profile 和传输结果。

##### 9. 性能回归与加压基线

第五阶段已消除两个固定约 5 秒等待，开发机 Private 手机热点最终基线约为启动 `0.396s`、停止 `0.173s`。第六阶段新增网络与防火墙诊断后不得重新引入固定等待。

性能回归采用两层标准：

- 通用受支持 `Private` LAN：启动若达到或超过约 5 秒视为不可接受，需要定位；停止目标保持秒级以内，若接近 2 秒应检查阻塞来源。
- 当前开发机 + 已验证手机热点：严格回归线暂定启动 `<= 1.0s`、停止 `<= 0.5s`。
- 任一单步骤若稳定落在约 `4.8–5.2s`，即使总耗时尚未越过更宽阈值，也按疑似固定 timeout 回归处理。
- Ethernet 的严格性能线不预先猜测；扩展坞/直连环境实测后建立独立基线。

##### 10. SMB 与 LanDrop 性能基准计划

SMB 仅作为可选的 Windows 原生文件共享性能参照，不是 LanDrop 功能验收前置条件，也不要求 LanDrop 必须达到 SMB 吞吐。若开发机的 SMB 共享能够在 `Private` Profile 下稳定保留，并仅通过目标接口/IP 在 Ethernet 与 WLAN 间切换使用，可以保留为长期基准工具；不得为了基准扩展到 `Public` 网络或引入不必要的匿名/宽泛共享策略。SMB 的具体安全配置与必要清理步骤在实际建立基准环境时单独记录。

LanDrop 上限测试采用分层方法，避免只看浏览器最终速度而无法定位瓶颈：

```text
1. iperf3 TCP             → 物理链路 / TCP 上限
2. 最小裸 Python HTTP      → Python + HTTP + 文件读取基线
3. LanDrop + curl          → Bottle/WSGI/认证/存储/统计核心链路
4. LanDrop + 浏览器         → 真实浏览器/Range/下载管理器体验
5. LanDrop 上传             → 浏览器原始请求流 + .part + 磁盘写入 + sync/rename（multipart 仅作兼容回退）
6. SMB（可选）             → Windows 原生文件共享横向参照
```

建议至少使用 `100 MB / 1 GB / 5 GB` 三档测试文件；条件允许时可增加更大文件。每组记录平均/峰值吞吐、总耗时、Python/总 CPU、网卡利用率、磁盘吞吐，以及传输后 SHA-256 完整性。尽量避免只连续读取同一个文件造成 Windows 文件缓存对结果的过度美化。

性能分析重点比较 `LanDrop / 裸 Python HTTP` 与 `LanDrop / TCP 链路能力`，SMB 用于参照而不是作为验收门槛。若 LanDrop 明显低于裸 HTTP，再定位 Bottle/WSGI、文件 I/O、认证/统计、浏览器 Range 或上传处理等具体层级。

2026-09-17 直连实测已经形成当前硬件组合的基线：`.2 → .1` iperf3 为约 `118.4–118.5 MB/s`，`.1 → .2` 为约 `87.4–88.1 MB/s`；最小 Python HTTP 下载约 `87.65–88.77 MB/s`，LanDrop 浏览器下载为 `86.25 MB/s`，SHA-256 一致。浏览器原始流上传客户端约 `118 MB/s`，GUI 端到端约 `105 MB/s`，SHA-256 一致；两种口径差异来自客户端发送进度与服务端 `.part` 写入、同步、最终改名的计时边界。由此可判定 LanDrop 两个方向均符合各自 TCP 基线。

旧 multipart 上传会由 Bottle 在生命周期计时前完整解析请求体，导致 GUI 把临时文件到接收目录的本地复制误报成约 `300–450 MB/s`。正式浏览器路径已改为 XHR `/upload/raw` 直读 WSGI 输入流并显示实时进度，multipart 仅保留为兼容回退。底层 `948/700 Mbit/s` 的方向差异尚不能精确归因到某一网卡或驱动设置，只记录为当前两机、网卡、驱动与 Windows 网络栈组合的实测事实；不为此修改系统高级网络设置，也不阻塞本阶段。

配置文件固定为 `%LOCALAPPDATA%\LanDrop\config.json`，使用 JSON。首版仅持久化共享目录、接收目录和上传上限；session 状态、当前 IP、倒计时、配对码等瞬时信息不得写入配置。配置缺失时使用默认值；配置损坏、字段缺失或值非法时回退到安全默认值并记录可理解的诊断，不得因配置错误开放更宽权限或阻止 GUI 启动。

本阶段增加一次性 QR 客户机邀请。二维码使用当前 LAN 地址的 `/pair/qr#<token>`，token 具备至少 128 bit 随机强度、仅存当前 session 内存且由服务机本地生成二维码。landing 页固定执行“读取 fragment → 保存到 JS 内存 → `history.replaceState()` 清除 fragment → POST 内存 token”。QR 与 8 位码共用唯一 pairing lock、同一 pairing revision 和同一可信客户机提交函数：先准备凭据与下一 revision，再以临时文件、`fsync` 和原子替换持久化可信记录，最终复核当前 session/revision 后才同步发布新 QR 与数字码并返回 Cookie；最终提交失败时恢复此前信任记录。已可信 Cookie 必须最先检查且不消费邀请。并发扫码只允许首个新客户机成功；任一路径成功后 QR 与数字码同时轮换，错误凭据不轮换。停服、到期、退出、session 或 endpoint 变化使旧邀请失效。QR token 不写入配置、日志、可信客户机文件、会话记录或复制诊断。项目不增加短 TTL、服务机人工确认或防截图/转发机制，其安全边界继续依赖 Private LAN、单次高熵凭据和 session/revision/endpoint 绑定。

QR 的主要交互对象是手机客户机；Windows 客户机默认直接输入主控页显示的访问地址，并使用可信 Cookie 或备用 8 位码。Windows 截图工具、视觉搜索或摄像头扫码不列为必测项。服务机 GUI 允许点击二维码进行纯本地放大，但不提供在线识别或把邀请链接复制到第三方服务的入口。

默认收发目录使用 Windows Known Folder 所解析的实际“下载”目录之下的 `LanDrop\Shared` 与 `LanDrop\Received`，显示上可简写为 `Downloads\LanDrop\Shared` 和 `Downloads\LanDrop\Received`。不得默认共享整个 Downloads，也不得依赖源码目录、PyInstaller `_internal` 或当前工作目录。程序仅可按需创建这两个明确属于 LanDrop 的子目录。

现有 `.part` 继续只表示“上传临时落盘 + 完成后原子提交”，不是续传状态。正常失败、客户机断开、停服和超限仍由既有 `finally` 清理；强杀进程、系统崩溃或断电可能留下孤立文件。主实例取得单实例所有权后，会在已配置接收目录第一层安全识别并清理**精确符合 LanDrop 自身临时命名规则且已超过 24 小时**的普通文件；不会按扩展名批量删除任意用户 `.part`，不会越出接收目录或跟随链接删除其他位置。上传仍不支持断点续传；下载已有 HTTP Range 基础能力，但完整可靠续传仍是未来增强项。

主程序 GUI 在本阶段完成视觉与信息架构收尾。主导航将高频的主控、信息与低频设置分区；主控页优先展示本次会话和可信客户机，目录、上传上限与 endpoint 等传输设置保留在主控页但默认折叠。主窗口、安装器和卸载器共用 Source Han 优先字体栈，并提供深蓝灰色、非纯黑的夜间配色；产品图标兼作三态主题控件，可在跟随 Windows、深色和浅色之间切换，纯视觉偏好不进入服务配置。第六阶段已有的多 endpoint 选择器只做视觉定稿与打包回归，不重新实现，也不预设单一 Private endpoint 时自动退化为只读显示。选择项继续展示接口别名、Windows 网络名称、IPv4 与类别，例如 `WLAN · Xiaomi 14 Pro · 10.146.168.152 · Private`。

### 第八阶段：安装器、卸载器与分发

第八阶段将第七阶段已经稳定的 `--onedir` 主程序推进为标准的 Windows 当前用户安装版。阶段目标不是重新设计传输协议，而是建立**固定安装位置、稳定系统入口、事务式升级、标准卸载登记、可控用户数据清理和最终发布验证**。详细执行顺序见 [第八阶段详细计划](PHASE8_TECHNICAL_SPIKE_TODO.md)。

本阶段核心方案已经冻结：

- 开发与安装生命周期继续使用 Python；不以 Inno Setup、NSIS 或 MSI 作为当前主路线。
- 正式安装后的主程序继续使用 Python 3.12 x64 + PyInstaller 6.22.3 `--onedir`，延续第七阶段已验证的资源和运行时结构。
- `LanDrop-Setup.exe` 与安装后的 `maintenance\Uninstall.exe` 使用 PyInstaller `--onefile --windowed`。Setup 对用户表现为单文件分发物，内部携带完整 onedir 主程序 payload、独立卸载器和构建清单。
- 安装范围为**当前用户**，固定程序根为 `%LOCALAPPDATA%\Programs\LanDrop`，不要求管理员权限；用户可变数据继续位于 `%LOCALAPPDATA%\LanDrop`。
- 正式程序布局使用稳定入口：

```text
%LOCALAPPDATA%\Programs\LanDrop\
├─ app\
│  ├─ LanDrop.exe
│  └─ _internal\
├─ maintenance\
│  └─ Uninstall.exe
└─ metadata\
   ├─ install.json
   └─ transaction.json   # 仅事务进行中存在
```

所有开始菜单、桌面快捷方式、自启动、`DisplayIcon` 等系统入口固定指向 `app\LanDrop.exe` 或 `maintenance\Uninstall.exe`，不得把版本号、 staging 路径或构建目录写入长期系统入口。

`metadata\install.json` 是**已经提交成功的当前安装状态**的唯一权威记录，只保存当前有效版本、构建标识、安装/更新时间、安装根和提交后的 `pending_cleanup`；它不承担未完成事务状态。安装/升级中间状态使用独立、严格命名并原子写入的 `metadata\transaction.json`，记录 `prepared → app_switched → integration_written → integration_verified` 等阶段。旧版 `install.json` 在整个升级提交阶段保持不动，首次安装则在最终提交前不存在正式 `install.json`；只有正式 app 自检和系统集成读回全部通过后，才原子发布新的 `install.json`。另在 `%LOCALAPPDATA%\LanDrop\logs\install-history.jsonl` 追加生命周期事件；该日志只用于审计和诊断，不反向驱动事务。

Setup、临时 Uninstall、LanDrop 正常启动和 `pending_cleanup` 共用一个独立于主程序单实例锁的 per-user 安装生命周期锁。Setup/Uninstall 在整个目录和注册表修改事务期间独占该锁，并在取得后再次确认 LanDrop 未运行。LanDrop 普通启动从进程入口开始取得该锁：若维护正在进行则用原生提示说明并退出；若取得成功，则在释放前先检查是否存在未完成或无法安全解释的 `transaction.json`，存在时提示“检测到未完成的安装/升级，请重新运行 LanDrop Setup 完成恢复”并退出。只有没有未完成事务时，才继续建立主程序单实例所有权和可供 Setup 检测的正式进程身份。LanDrop 执行 `pending_cleanup` 前也必须重新取得同一个锁，从而关闭双方“检查完成后对方才启动”的 TOCTOU 窗口。

`LanDrop.exe --self-check` 是唯一例外：它是由 Setup 从正式 app 路径启动的无副作用维护验证模式，不进入普通 LanDrop 启动路径，不取得主程序单实例，不启动 GUI、托盘或服务，不执行 `pending_cleanup`，也不因生命周期锁已由父 Setup 持有而失败。Setup 不得为了执行 self-check 临时释放生命周期锁。

安装器继续复用第七阶段已经建立的 `ui/setup/`、`ui/uninstall/` 与 `ui/wizard/` 视觉资源。WebView2 Runtime 作为外部前置条件：`README-release` 明确声明 Windows 11 正常环境通常已具备该运行时；Setup、主程序和 Uninstall 在导入/初始化 pywebview 前做本地检查。项目不捆绑 Runtime、不自动下载、不要求安装器联网，也不实现卸载器缺少 WebView2 时的另一套卸载 UI。若 Runtime 缺失，Uninstall 必须用原生 `MessageBoxW` 明确提示用户重新安装或修复 Microsoft Edge WebView2 Runtime 后再次卸载，不能无反馈退出。

安装采用“先 staging，后提交”的完整迁入方式。Setup 先把新 payload 释放到严格命名的 `.staging-<version>-<transaction>`，根据构建清单逐项验证文件和 SHA-256；只有验证通过后才进入正式安装或升级提交。安装器不得把来源不明、校验不完整的 payload 直接写进正式 `app`。

首次安装提交过程中，Setup 在当前用户范围建立标准 Windows 集成；只有这些对象写入并读回验证、正式 `install.json` 原子发布以后，首次安装才算完成：

- 必建当前用户开始菜单快捷方式；桌面快捷方式作为安装选项，默认不勾选；
- 继续使用稳定 AUMID `LanDrop.Desktop`，验证快捷方式、当前进程和 Windows-Toasts 的通知身份一致；
- 首次安装按既定方案在 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 注册 `LanDrop.exe --startup`，使用户能够在 Windows“启动应用”/任务管理器启动页禁用；升级默认保留当前自启动状态，不写或重置 `StartupApproved`。稳定路径未变化时不重写 Run；若用户已经禁用或主动删除 Run，LanDrop 和 Setup 都不得自行恢复，除非用户在 Setup 中明确重新选择启用；
- `--startup` 只启动桌面程序并进入托盘，传输服务默认关闭，TCP 8000 不监听；
- 在 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\LanDrop` 登记 `DisplayName`、`DisplayVersion`、`Publisher`、`DisplayIcon`、`InstallLocation`、`UninstallString`、`EstimatedSize` 等标准字段，第一版使用 `NoModify=1`、`NoRepair=1`；
- 编码前形成明确的系统集成对象清单；当前确定对象仅包括开始菜单 `.lnk`、可选桌面 `.lnk`、HKCU Run 和 HKCU Uninstall。`SetCurrentProcessExplicitAppUserModelID` 是运行时调用，不是卸载对象；Toast 若最终需要快捷方式 Property Store、注册表或 COM 激活登记，必须按实际实现把精确对象追加到清单，卸载器不得使用泛化的“通知身份相关安装项”猜测删除；
- 目标是让当前用户在 Windows 设置“已安装的应用”和控制面板“程序和功能”中都能看到 LanDrop，并从两个入口调用同一个卸载器。

防火墙与网络边界继续完全沿用第六、七阶段：**Setup、LanDrop、Uninstall 都不创建、修改或删除防火墙规则，不修改 Private/Public、代理、VPN 或静态 IP。** 首次正式 `LanDrop.exe` 监听 TCP 8000 时，如果 Windows 自身显示网络访问授权提示，由用户选择；不同机器/策略下提示是否出现不作为程序逻辑假设。干净机发布验收需要观察实际 Windows 行为、必要时检查系统生成的规则，并验证拒绝或无规则时 LanDrop 的只读诊断和设置入口仍然有效。

升级和卸载不新增 IPC。Setup 或 Uninstall 只按正式 `LanDrop.exe` 路径检查现有进程；如果程序仍在运行，流程停止并提示用户从系统托盘退出后重试。不得发送 `WM_CLOSE` 代替退出，不得自动 Kill。LanDrop 自身的托盘“退出”在存在活动上传/下载时必须明确提示“退出将中断当前传输”，只有用户确认后才进入已有统一 `request_exit()` 清理路径；取消则保持程序和传输不变。

升级使用**事务级版本隔离**，但不长期保留多个版本。正常状态只存在一个正式 `app`。升级时流程固定为：

```text
取得安装生命周期锁
→ 创建 transaction.json
→ 新版写入 .staging-<new-version>-<transaction>
→ 验证 staging 中的新 payload
→ 确认 LanDrop 已完全退出
→ 当前 app 与 maintenance 整体迁到 .rollback-<old-version>-<transaction>
→ staging 中的 app 与 maintenance 整体切换到正式路径
→ 从正式 app 路径执行 LanDrop.exe --self-check
→ 写入卸载登记版本信息和其他必要系统状态
→ 逐项读回验证系统集成
→ 原子发布新的 install.json
→ 写 upgrade_committed / installed 历史
→ 删除 staging，并尝试删除 rollback
→ rollback 已不存在，或已原子登记到 install.json.pending_cleanup
→ 最后删除 transaction.json
```

如果新版本提交或系统集成验证失败，必须撤回失败的新 `app` 与 `maintenance`，将 `.rollback-*` 中的二者共同恢复，并恢复安装前可恢复的系统登记。`maintenance\Uninstall.exe` 属于随版本升级的正式 payload，不允许形成“app B + Uninstall A”。禁止把新版文件直接混合覆盖到旧 `_internal`，也不建立长期 `versions\0.x\...` 历史仓库。版本历史由 `install.json` / `install-history.jsonl` 记录，而不是保留旧程序目录或空版本目录。

升级提交成功后旧 `.rollback-*` 必须清理。若因 Defender、索引器或临时文件句柄导致删除失败，可以把应用升级状态记为已提交，但必须在 `install.json` 中登记 `pending_cleanup` 并写入 `install-history.jsonl`；后续 Setup 启动或 LanDrop 取得单实例所有权后再次尝试清理。只有 rollback 已不存在，或其所有权已通过原子写入且读回确认可靠移交给 `install.json.pending_cleanup` 后，才允许删除 `transaction.json`；pending 写入失败时必须保留事务文件，不能留下无人解释的 rollback。清理器只允许处理安装根内严格符合 LanDrop 命名规则的 `.staging-*` / `.rollback-*` 普通目录，必须拒绝 symlink、junction/reparse point 和路径越界，不得让旧 payload 随升级次数长期累积。

卸载器采用“先迁出，再删除程序根”的完整迁出方式。安装目录内的 `maintenance\Uninstall.exe` 先确认 LanDrop 未运行，再生成带创建/过期时间、原卸载器 PID、安装根、当前版本/build id、用户数据选择和源卸载器哈希的规范化 request JSON，把自身与 request 复制到 `%TEMP%\LanDrop\uninstall-<random-id>\`，并通过命令行把独立的随机 nonce 与 `expected_request_sha256` 交给临时副本。临时 Uninstall 验证 request、时效、路径及自身 SHA-256 与源卸载器一致后，必须先取得安装生命周期锁，再重新读取当前权威 `install.json`，确认 product id、version/build id 和固定安装根仍与 request 一致；若安装状态已变化、`transaction.json` 存在或状态无法安全解释，则拒绝旧 request，并要求用户从当前 Windows 卸载入口重新启动 Uninstall。该绑定用于防止陈旧请求、路径错配和异常交接，不扩展成抵御恶意本机用户的复杂认证协议。验证全部通过后，临时副本才严格按系统集成对象清单清理并删除整个 `%LOCALAPPDATA%\Programs\LanDrop`。

程序根、事务目录和用户数据删除统一使用同一套路径安全规则：canonical path 必须落在预期产品根；不跟随 symlink、junction 或其他 reparse point；遇到未知 reparse object 宁可终止并报告残留，不继续递归删除。临时卸载器退出后，再由系统现成的无窗口清理步骤删除临时卸载目录。

卸载 UI 必须继续明确区分“删除程序”和“删除用户数据”。配置、日志、可信客户机数据按用户选择处理；如选择删除，只能在 `%LOCALAPPDATA%\LanDrop` 的已知产品范围内执行白名单清理。保留日志时，`install-history.jsonl` 持久记录 `uninstall_started/uninstall_completed`；删除日志时不承诺永久保存 `uninstall_completed`，本次结果由临时卸载日志和完成页表达，随后随临时目录清理。无论任何卸载选择，`Downloads\LanDrop\Shared`、`Downloads\LanDrop\Received` 及用户自定义的实际共享/接收目录都视为用户文件，**绝不由卸载器删除**。

第八阶段实施和测试顺序固定为：**冻结安装契约与目录 → 安装状态/历史 → Setup payload 与首次安装 → HKCU 系统集成 → 自启动/AUMID/快捷方式 → 运行中阻断与托盘退出确认 → 事务升级/回滚/旧 payload 清理 → 临时卸载器与用户数据选择 → 自动化和本机生命周期回归 → 干净 Windows 11 完整发布验收**。

最终发布验收必须同时补齐第七阶段延期项：在没有源码、venv 或独立 Python 的干净 Windows 11 环境中，从单个 `LanDrop-Setup.exe` 开始完成安装、首次运行、WebView2 检测、Private 实际传输、Windows 原生防火墙行为、自启动但服务关闭、Public 拒绝、升级、卸载和系统状态恢复。该门槛完成前，不得宣称正式发布验收结束。

| 2026-09-20 | 自启动使用当前用户 Windows 启动项，允许任务管理器“启动应用”直接禁用 | 登录后只进入托盘且服务保持关闭；用户禁用后 LanDrop 不自动恢复启动项 |

## 10. 下一步

第八阶段核心方案已冻结。下一步按 [第八阶段详细计划](PHASE8_TECHNICAL_SPIKE_TODO.md) 顺序实施：先落地安装布局、payload 清单、`install.json`/`install-history.jsonl` 和单文件 Setup；再建立 HKCU 卸载登记、开始菜单/可选桌面快捷方式、`LanDrop.Desktop` 通知身份及可由任务管理器禁用的登录启动；随后实现运行中阻断、托盘活动传输退出确认、staging/rollback 升级、`pending_cleanup` 和临时卸载器完整迁出。
