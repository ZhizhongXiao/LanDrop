# 第七阶段详细计划：配置与用户目录、GUI/Web UI 定稿、便携打包与稳定性测试

状态：**核心实现、桌面/移动界面人工回归与本机正式便携构建回归已完成；因第二台干净 Windows 11 电脑暂不可用，正式无开发环境验收延期，但允许进入第八阶段开发（2026-09-20）**。

前置条件：第六阶段 `0.6.0` 已完成验收，65 项自动化测试以及 Private WLAN、手机热点、PC↔PC Ethernet、网络变化、防火墙异步诊断和原始流上传边界均已通过。第七阶段不得重新设计核心传输协议，也不得削弱现有 Private/Public 安全边界、生命周期、托盘/Toast、endpoint 冻结和统一退出语义。

## 目标

把 LanDrop 从“源码开发环境中功能完整”推进为“设置可跨启动保留、用户目录稳定、Windows GUI 与移动 Web UI 基本定稿、无需 Python 开发环境即可在另一台 Windows 11 电脑运行、并经过重复使用与长期稳定性验证”的便携版本。

本阶段顺序固定为：

```text
小范围设置持久化 / 用户目录化
→ Windows GUI / 移动 Web UI 收尾
→ 资源与路径整理
→ 便携打包
→ 单实例与打包差异修正
→ 干净环境验收
→ 稳定性 / 长时间 / 重复操作回归
```

安装器和卸载器的正式实现留在第八阶段。第七阶段末尾可以先绘制其界面草图，以复用主窗口计划采用的 LanDrop 视觉语言，但不提前引入安装、升级、注册表清理或卸载逻辑。

## 一、实施前需要冻结的关键决策

### P7-D01：打包形态

建议第一版使用 **PyInstaller `--onedir`**：

- 便于检查 pywebview、pystray、Windows-Toasts、Bottle、图标和 Web 静态资源是否遗漏；
- 便于直接观察 DLL、资源和运行时文件；
- 故障定位成本低于 `--onefile`；
- 第七阶段首先验证“可靠便携运行”，不追求单 EXE 形式。

`--onefile` 仅作为后续可选优化，不是本阶段验收条件。

可重复构建基线必须包含：

- Python 3.12 x64；
- 经最小技术验证后冻结并记录的明确 PyInstaller 版本；
- 纳入版本控制的 PyInstaller spec；
- 纳入版本控制的 build script，不以一次性终端命令作为正式构建方法；
- 构建时记录 LanDrop 版本、Python/PyInstaller 版本和输出目录。

已冻结：第七阶段首个打包目标采用 PyInstaller `--onedir`；构建基线为 Python 3.12 x64 与 PyInstaller 6.22.3。项目使用纳入版本控制的 `LanDrop.spec` 和 `scripts/build-portable.ps1`，构建后自动执行无窗口自检并生成 `build-info.json`。

### P7-D02：配置与便携版数据位置（已冻结）

程序资源与用户可变数据必须分离：

- 程序目录：EXE、DLL、图标、`ui/` 下拆分的 HTML/CSS/JS 和其他只读资源；
- `%LOCALAPPDATA%\LanDrop\config.json`：JSON 格式的用户设置；
- `%LOCALAPPDATA%\LanDrop\logs`：普通诊断、异常与必要的调试日志；
- `%LOCALAPPDATA%\LanDrop` 下既有凭据位置：可信客户机数据；
- 用户选择的共享/接收目录：实际文件数据；
- 不因“便携版”而把日志、凭据、配置或状态强制写到 EXE 旁边。

首版 `config.json` 只持久化真正需要跨启动保留的设置：

- 共享目录；
- 接收目录；
- 上传上限。

session 状态、当前 IPv4、倒计时、配对码、当前 endpoint 和正在传输的任务均为瞬时信息，不得持久化。配置缺失时使用默认值；JSON 损坏、字段缺失、类型错误或值越界时回退到安全默认值，记录可理解的诊断，并保证 GUI 仍可启动。

默认目录必须通过 Windows Known Folder API/等价可靠方式解析用户实际“下载”目录，再使用：

```text
Downloads\LanDrop\Shared
Downloads\LanDrop\Received
```

不得假定系统目录的显示名必为英文，不得默认共享整个 Downloads，也不得把源码目录、当前工作目录或 PyInstaller `_internal` 当作默认收发目录。程序只按需创建上述明确属于 LanDrop 的子目录；用户仍可在 GUI 中选择其他目录并由配置持久化。

### P7-D03：干净测试环境

建议以另一台 Windows 11 电脑作为正式干净环境，要求：

- 不复制项目源码；
- 不依赖项目 venv；
- 不要求用户单独安装 Python；
- 检查 Microsoft Edge WebView2 Runtime 是否可用；若缺失，程序应给出可理解说明，不以无响应或空白窗口结束；
- 可以使用系统自带 Windows PowerShell 和 Windows 设置；
- Windows 防火墙保持开启；
- 测试网络仍以用户信任的 `Private` WLAN/Ethernet 为唯一支持场景。

已确定第二台 Windows 11 电脑作为正式无 Python、无源码验收机；当前该设备暂不可用，因此 P7-S10 至 P7-S12 的干净环境整体验收延期。延期不阻塞第八阶段设计、编码和本机测试，但在正式发布前必须使用干净环境同时完成便携版与安装版/卸载版联合验收，不得因先进入第八阶段而把本项视为通过。

### P7-D04：单实例行为

第七阶段必须解决重复启动。最低要求：

- 第二次启动不得创建第二套 ServiceController；
- 不得出现两个托盘图标；
- 不得让两个实例争抢 TCP 8000；
- 不得生成两套生命周期和 Toast 状态。

建议优先行为：**再次双击 LanDrop 时唤起已有 GUI，然后新进程立即退出。**

如果该行为需要引入明显复杂的 IPC，也可以退化为“明确提示 LanDrop 已在运行后退出”；但必须在编码前冻结，不能继续保留未定义行为。

### P7-D05：便携版系统权限与诊断边界（已冻结）

- LanDrop 继续只检测、解释和引导，不主动修改网络类别、防火墙、代理或 VPN。
- 便携版不创建防火墙规则。首次监听 TCP 8000 时若 Windows Defender Firewall 弹出授权提示，由用户自行选择仅允许 `Private` 网络通信。
- 如果客户机访问被阻止，信息页解释当前防火墙证据与“不确定”边界，并提供 Windows 防火墙设置入口；不得自动提权或替用户放行。
- 无控制台构建的普通诊断与异常写入 `%LOCALAPPDATA%\LanDrop\logs`，不再依赖终端输出。
- 信息页只展示高价值摘要，并提供“查看详细诊断”“打开日志文件夹”“复制诊断信息”。复制内容必须排除配对码、凭据等敏感信息，并避免无必要暴露完整个人路径。

## 二、GUI 与视觉收尾

### P7-S01：主程序信息架构冻结

保持第六阶段已经形成的三页结构：

- **主控**：服务启停、倒计时、收发目录、当前 endpoint、配对信息、可信客户机和高频操作；
- **信息**：当前服务网络、其他 LAN、IPv4/Profile、防火墙证据、TUN/VPN、监听和传输统计；
- **设置**：LanDrop 自身重新检测/重试，以及 Windows 网络、防火墙、代理等官方设置入口。测试与调试入口不是当前功能；如后续确有需要，必须作为新增功能单独设计。

不得因为视觉调整重新引入第四、五、六阶段已经解决的状态语义分裂。

### P7-S02：已有多 endpoint 选择器的视觉定稿与打包回归

第六阶段已经实现并验收多 endpoint 选择器。第七阶段不重新实现选择逻辑，也不预设仅有一个合法 Private endpoint 时自动退化成只读显示；当前下拉选择形式继续保留并完成视觉定稿。选项应同时显示接口别名、Windows 网络名称、IPv4 与类别，例如：

```text
WLAN · Xiaomi 14 Pro · 10.146.168.152 · Private
以太网 2 · 未识别的网络 · 192.168.50.1 · Private
```

仅有一个合法 Private endpoint 时允许沿用“自动选择”；存在两个及以上合法 Private endpoint 时由用户明确选择。选择器只在服务停止状态可修改。服务启动后本次 session 冻结 `InterfaceIndex + IPv4 + NetworkCategory`，禁止热迁移。打包回归需确认网络名称、禁用状态和刷新行为与源码版一致。

重点收尾：

- 中文/英文路径和长文件名的排版；
- 按钮层级、危险操作区分、禁用状态；
- 空状态、检测中、无法确定、警告、错误、正常状态；
- 主图标、托盘图标与窗口图标；

- 保证 GUI 刷新不重建窗口、不破坏展开状态和正在进行的传输。

### P7-S04：一次性 QR 客户机邀请（已冻结、实现并通过手机实测）

QR Code 是当前 Private LAN session 内的一次性客户机邀请。二维码内容为当前 LAN 地址的 `/pair/qr#<token>`；token 使用至少 128 bit 随机强度并仅存当前进程内存，fragment 由 landing 页先读入 JS 内存、再通过 `history.replaceState()` 从地址栏清除，最后才以 POST 提交。页面和响应使用 `Cache-Control: no-store` 与 `Referrer-Policy: no-referrer`，二维码完全在本地生成，不调用在线服务。

QR 与备用 8 位码共用唯一 pairing lock、同一个 pairing revision 和同一个成功提交函数。服务端先检查现有可信 Cookie；已可信客户机直接进入文件页，不验证或消费邀请。新客户机在统一事务内校验当前 session/revision/credential，准备可信凭据和下一 revision，使用可信客户机文件既有的临时文件、`fsync` 与原子替换持久化，再次确认 session/revision 后才同步发布新 QR token 与数字码；只有两侧全部提交成功才返回 `Set-Cookie`。若会话失效或最终提交失败，则恢复此前可信客户机文件，且不得消费当前邀请或向浏览器发放 Cookie。

同一 QR 只允许一个新客户机成功；并发扫描由统一锁保证只有首个提交成功。手动码或 QR 任一路径成功后，旧二维码与旧数字码同时失效。错误 token、旧 revision、错误 POST 或手动输错数字码不触发轮换。停服、到期、退出、session 替换以及 endpoint/IP/NetworkCategory 变化都会使旧邀请失效。QR token 不进入配置、日志、可信客户机文件、会话记录或复制诊断。

产品不试图阻止二维码截图、拍照、转发或二次扫描，也不增加短 TTL 或服务机人工确认；安全边界由 `Private LAN + 高熵 token + session/revision/endpoint 绑定 + 单次消费 + 成功同步轮换 + 停服/换网失效 + 凭据不记录不持久化` 共同承担。

产品交互上，QR 主要面向手机客户机；Windows 客户机通常直接输入主控页显示的客户机访问地址，并在首次连接时使用备用 8 位码。Windows 截图工具、Bing 视觉搜索或摄像头扫码不作为阶段必测条件。二维码点击后可在服务机本地放大，便于手机或具备扫码能力的设备识别，但不增加复制邀请链接或在线解析入口。

通过标准：主程序 GUI 进入**视觉冻结**，之后第七阶段仅因缺陷修正而调整，不再大幅重构布局。

### P7-S04：移动 Web UI 定稿

移动端以竖屏 Android 浏览器为主要形态，同时保持 Windows 浏览器客户机可用：

- 使用单栏、适合触控的布局，文件名占主要宽度，大小和状态作为次级信息；
- 文件列表增加复选框与固定在底部的批量操作栏；
- 批量下载必须先由用户确认，单文件下载也应保持在当前文件列表页；
- 下载继续使用浏览器原生 HTTP 下载、`Content-Disposition` 与现有 HTTP Range，不采用 JS Blob 或前端大文件流式接管；
- 不默认并发启动多个下载；浏览器对多次下载的权限提示必须纳入人工验收；
- 多文件上传使用浏览器多选与前端串行队列，展示当前文件、单文件结果和整批进度；
- 后端仍保持“一文件一 `/upload/raw` 请求、一文件一个 `.part`、一次原子提交”，前端不得把批量操作扩展成新的打包或并发传输协议；
- 失败时允许继续后续文件或停止整批，但最终交互必须明确显示已成功、失败与未开始项，不能以底层 HTTP 请求数量替代文件任务状态。

移动页面通过标准：单文件下载不会导航离开文件列表；批量下载与串行多文件上传在手机上可理解、可取消/重试且不会破坏既有配对、生命周期和统计语义。

## 三、资源与路径打包准备

### P7-S05：资源清单与路径规范

建立明确资源清单，至少包括：

- `LanDrop.ico`；
- `ui/desktop/` 下的主窗口 HTML、CSS 与 JavaScript；
- `ui/wizard/`、`ui/setup/`、`ui/uninstall/` 下的安装器/卸载器视觉草图资源；
- Bottle/pystray/Windows-Toasts 等运行依赖；
- 默认页面、内置文本和其他只读资源。

已按新增 UI 重构任务将 pywebview 前端从 `landrop/gui.py` 拆分：Python 文件只保留窗口、协调器与受控 JS API；`ui/desktop/index.html` 负责语义结构，`css/` 按设计令牌、窗口壳层、组件拆分，`js/` 按状态渲染和事件绑定拆分。安装器/卸载器草图使用独立页面并共用 `ui/wizard/`。`LanDrop.spec` 整体收集 `ui/`，便携自检检查主窗口关键资源；拆分后须重新完成源码和打包版 GUI 回归。

代码不得假设当前工作目录等于程序目录。至少验证：

1. 从源码目录运行；
2. 从其他工作目录启动；
3. 打包目录整体移动后启动；
4. 程序路径包含空格；
5. 程序路径包含中文。

### P7-S06：用户数据路径、配置与孤立临时文件

确认日志、配置、可信客户机等写入用户数据目录，不因打包位置不同而丢失或写入只读目录。移动便携程序目录后，已有用户状态的保留行为必须明确、可解释。至少验证：

- 首次启动创建安全的默认 `config.json` 或在首次修改设置时原子写入；
- 修改共享目录、接收目录和上传上限后重启仍保留；
- session、IPv4、倒计时和配对码不会跨启动恢复；
- 配置损坏、部分字段缺失或非法值时回退到安全默认值；
- 默认收发目录位于实际 Downloads 下的 `LanDrop\Shared` 与 `LanDrop\Received`，不会暴露整个 Downloads；
- 从不同 cwd、移动后的便携目录和只读程序目录启动时，用户数据位置不变。

现有上传临时文件名为 `.<safe_name>.<24 位小写十六进制随机串>.part`。它只用于临时落盘和完成后的原子提交，不是续传记录。正常失败、断开、停服和超限仍由上传流程的 `finally` 清理；强杀、系统崩溃或断电可能留下孤立文件。

启动清理必须满足以下边界：

1. 只在成功取得单实例所有权后执行，避免与另一个仍在写入的 LanDrop 进程竞争；
2. 只检查当前已配置的接收目录，不递归越出该目录；
3. 只清理名称精确符合上述 LanDrop 临时命名规则的普通文件；
4. 不跟随符号链接/重解析点，不删除任意用户自行创建的 `*.part`；
5. 只清理最后修改时间已超过 24 小时安全阈值的匹配文件，避免误碰同时运行的 CLI 或其他尚未结束的写入；
6. 清理成功、跳过和失败均写入诊断日志，但不因单个文件无法删除而阻止 GUI 启动。

上传仍不支持断点续传。下载已有 HTTP Range 基础，能否续传由浏览器及服务仍可访问的同一文件共同决定；“完整可靠续传”继续作为未来增强项。

## 四、便携打包

### P7-S07：建立首个 `--onedir` 构建

要求：

- 不安装额外 Python 即可启动；
- 启动无缺失模块/DLL/资源异常；
- pywebview 正常创建窗口；
- pystray 托盘正常；
- Windows Toast 正常初始化；
- Bottle 服务、上传/下载、日志与设置均正常；
- 不使用管理员权限作为正常启动前提。

正式便携版采用无控制台构建时，诊断输出必须有明确去向：用户可处理的错误优先显示在 GUI；GUI 创建前的启动失败与技术诊断写入 `%LOCALAPPDATA%\LanDrop\logs\application.log`；现有启动/停止性能分段输出默认关闭，仅在显式调试模式下记录。不得继续把终端作为正式版唯一错误通道。

构建脚本和 PyInstaller spec 文件应纳入项目，禁止只保留一次性的手工命令。

### P7-S08：打包后的 Toast / AUMID

源码环境已经验证的 Toast 行为必须在打包 EXE 中重新验证：

- 即将到期通知；
- “重置为 5 分钟”；
- “立即关闭”；
- 自动关闭无按钮通知；
- 点击正文只打开现有 GUI；
- 旧 session/revision 动作不能修改当前服务；
- 正常退出和下次启动能清理遗留通知；
- 程序目录移动后通知行为仍可解释。

如果打包环境要求稳定安装路径或正式注册才能获得理想通知身份，应记录为第八阶段安装器的输入条件，而不是在第七阶段偷偷引入安装行为。

## 五、单实例与重复启动

### P7-S09：单实例实现与竞态

至少覆盖：

1. LanDrop 空闲时再次双击；
2. 服务运行时再次双击；
3. 正在上传/下载时再次双击；
4. GUI 隐藏到托盘时再次双击；
5. 第一个实例正在退出时快速再次启动。

通过标准：始终只有一个有效应用实例、一套托盘和一套 ServiceController；第二次启动不能改变现有 session 状态或制造端口争用。

## 六、干净 Windows 环境验收

### P7-S10：无开发环境启动

在另一台 Windows 11 电脑上，只复制便携目录，不复制源码/venv，不单独安装 Python。验证：

- 双击可启动；
- GUI/托盘/通知可用；
- `%LOCALAPPDATA%\LanDrop` 可正确创建；
- 程序退出后无残留进程；
- TCP 8000 正确释放。

### P7-S11：网络与防火墙回归

无条件必测：

- Private WLAN 或 Private Ethernet 至少一种正常启动并完成实际传输；
- Public 明确拒绝；
- selected endpoint 变化后 `network_changed`；
- 防火墙深度诊断异步、超时可降级；
- Windows 网络/防火墙/代理设置入口有效。

测试机条件具备时补测，不作为单台干净机器的无条件门槛：

- 另一种物理网络（WLAN 或 Ethernet）；
- WLAN + Ethernet 多候选选择；
- TUN/VPN 存在但不误选。

首次监听若出现 Windows Defender Firewall 授权提示，由测试者自行选择 `Private`；LanDrop 本体不得自动创建或修改系统规则。另需验证拒绝/未放行时信息页能解释状态，并可打开 Windows 防火墙设置。

### P7-S12：核心传输回归

至少完成：

- 配对与持久信任；
- 取消信任后重新配对；
- 浏览器下载；
- 原始流上传；
- 中文/特殊文件名；
- 同名文件策略；
- 1 GB 级文件 SHA-256 完整性；
- 上传超限 413；
- 传输中手动停止；
- 生命周期到期与宽限；
- GUI 隐藏到托盘时传输继续。

移动 Web UI 还需回归：单文件下载留在列表页、复选与批量下载确认、多文件上传选择与串行队列、逐文件结果和整批进度；后端请求与 `.part`/原子提交语义保持一文件一份。

## 七、稳定性与长期回归

### P7-S13：重复启停与窗口操作

建议最低：

- 服务启动/停止 30 次；
- GUI 显示/隐藏 30 次；
- 托盘打开窗口 20 次；
- 倒计时 reset 20 次；
- 多个 session 连续自然到期。

过程中检查内存异常增长、重复线程、重复托盘、端口残留和 Toast 堆积。

### P7-S14：传输稳定性

建议：

- 连续多次 1 GB 下载；
- 连续多次 1 GB 上传；
- 至少一次上传/下载过程中停止；
- 至少一次传输过程中隐藏/恢复 GUI；
- 至少一次网络变化导致自动关闭；
- 可选 5 GB 和并发测试作为压力扩展，不阻塞首个便携版验收。

### P7-S15：长时间空闲

让应用保持托盘运行、服务停止状态数小时，确认：

- CPU 保持低占用；
- 无周期性 PowerShell 高频调用；
- 无 Toast/线程泄漏；
- 再次打开窗口和启动服务仍正常。

### P7-S16：异常退出与恢复

验证：

- 强制结束进程；
- 下一次启动清理旧 Toast；
- 无旧 TCP 监听；
- 信任数据与日志没有损坏；
- 人工放置的不匹配 `.part` 保留，只有精确匹配 LanDrop 命名规则的孤立普通文件被安全清理；
- 再次启动不会因单实例锁残留而错误拒绝。

## 十、执行规则

- 第七阶段不新增 Public 网络支持、HTTPS、账号体系、高并发、完整可靠续传、自动更新或安装器底层逻辑。
- 配置只保存冻结的三类设置；不得把 session、网络地址、倒计时、配对码或活动任务变成恢复状态。
- `.part` 继续只承担上传临时落盘与原子提交；启动清理不得扩大为通配删除用户文件。
- 移动 Web UI 只编排既有单文件 HTTP 传输，不引入 JS Blob、大文件前端流接管或默认并发。
- 便携版不主动创建、修改或删除防火墙规则；系统配置仍只检测、解释和引导。
- GUI 收尾在打包前完成；便携版开始正式验收后，不再无目的重构主界面。
- 第八阶段为正式后续阶段；安装器/卸载器视觉可以提前设计，但正式实现统一留在第八阶段。
- 发现仅在打包环境出现的问题时，优先修资源定位、依赖收集、进程模型和 Windows 集成，不复制第二套业务逻辑。
- 每个稳定性测试仍遵循“一次只改变一个主要变量”，并记录版本、机器、网络、路径和实际结果。
- 若打包要求管理员权限、自动改防火墙或固定注册表状态才能运行，应暂停实现并先重新评估产品边界。
