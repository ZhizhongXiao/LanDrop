# 局域网文件传输工具：开发总计划

> 文档状态：修订稿 v3（持续记录阶段实施结果）
> 适用对象：具备基础 Python 使用经验、暂不了解计算机通信原理的个人开发者  
> 当前进度：第五阶段“托盘与 Windows 通知”已于 2026-09-17 完成验收，准备进入第六阶段
> 暂定平台：Windows 11 + Android 手机  

## 1. 项目目标

开发一个以 Python 局域网 HTTP 服务为核心的 Windows 小工具，让电脑与手机在可信的局域网中方便地传输文件。首要支持家庭 `Private` 网络和用户自有手机热点；不以陌生 `Public` 网络作为运行场景。

最终希望具备以下使用流程：

1. 在电脑上选择共享目录和接收目录。
2. 点击“开启传输”。
3. 程序显示访问地址和二维码。
4. 手机通过浏览器访问，下载电脑文件或上传手机文件。
5. 服务默认运行 5 分钟。
6. 即将到期时，Windows 通知允许“重置为 5 分钟”或“立即关闭”。
7. GUI 窗口关闭后隐藏到系统托盘，需要时可以重新打开。
8. 服务到期后关闭监听端口，托盘程序继续等待下一次启动。

这个项目首先服务于开发者本人，不以立即发布成熟商业软件为目标。

## 2. 开发原则

### 2.1 一次只解决一层问题

先确认文件传输链路可用，再加入上传、GUI、托盘、通知以及网络与防火墙诊断。不得在核心功能尚未稳定时同时堆叠所有功能。

### 2.2 每个阶段都必须可以独立运行和验收

每完成一个阶段，都要保留一个可运行版本。后续功能出现故障时，可以回到前一阶段定位问题。

### 2.3 可信专用网络优先

程序仅面向用户信任的 `Private` 网络运行，主要场景包括家庭 Wi-Fi 和用户自有手机热点。`Public` 网络不作为后期高级功能，而是明确列入本项目的不支持范围。若电脑当前连接被 Windows 标记为 `Public`，程序不启动文件传输服务，只解释原因并提供 Windows 设置入口。

### 2.4 安全边界优先于功能数量

程序只能访问用户明确选择的目录。不得因为方便而开放整个磁盘、任意系统路径或远程命令执行能力。

### 2.5 重要状态必须在界面中说清楚

不使用含义模糊的“已连接”。应分别显示服务器状态、监听地址、网络类型、防火墙状态、剩余时间和正在传输的文件。

### 2.6 面向初学者保留实验记录

遇到问题时先记录现象、测试条件和结果，再修改代码。每次只改变一个主要变量，避免不知道究竟是哪项修改解决了问题。

### 2.7 系统网络配置只检测、不代改

程序只读取 Windows 当前网络类别、防火墙状态、活动网卡和 IPv4，并在需要时打开对应的 Windows 官方设置入口。程序不自动把 `Public` 改成 `Private`，不自动关闭防火墙，也不以管理员权限替用户修改防火墙规则。用户完成系统设置后，由程序重新检测实际状态。

### 2.8 轻量化优先，不为理论风险堆叠体系

项目定位是把 `python -m http.server [端口]` 式的临时局域网传输体验做得更顺手，而不是重新实现 SMB、就近共享或企业级文件传输平台。安全设计以“避免误操作、限制暴露范围、可信 Private 网络内可用”为目标，不引入账号体系、复杂权限模型、证书基础设施或大量高级配置。

第一阶段继续使用 `python -m http.server` 或标准库等价实现作为最小链路验证工具，用于确认 LAN 可达性、监听地址、下载行为和网络诊断基线。

从第二阶段开始，正式 HTTP 应用层优先采用 **Bottle**。选择 Bottle 的原因是：它保持单文件、轻量、无额外第三方依赖链的特性，同时直接提供路由、文件上传、Cookie、静态文件服务等能力，可以避免手写 `BaseHTTPRequestHandler` 时反复处理 Cookie、multipart 上传、路径安全和 URL 分派等细节。除非后续需求明显超出 Bottle 的能力，否则不再把 Flask/FastAPI 作为当前路线。

### 2.9 网络环境变化不做热迁移

程序每次启动服务时重新检测当前活动局域网、IPv4 和网络类别，不保存固定 LAN IP。若服务运行期间发生 Wi-Fi 切换、热点切换、IPv4 变化或活动网卡变化，当前会话直接终止，旧地址和二维码失效；用户重新点击“开启传输”后重新检测并启动。项目不开发跨网卡热迁移。

## 3. 已确定的产品边界

### 3.1 已确定内容

- 开发语言使用 Python。
- 目标系统首先是 Windows 11。
- 手机端首先使用浏览器，不开发 Android App。
- 最终桌面 GUI 倾向使用 pywebview + HTML/CSS/JavaScript。
- 程序采用“需要时开启，不用时关闭”的临时服务模式。
- 单次服务默认维持 5 分钟。
- GUI 可以隐藏到 Windows 系统托盘。
- 即将到期时使用 Windows 通知提醒关闭或将倒计时重置为 5 分钟。
- 支持可信 `Private` 网络，主要包括家庭 Wi-Fi 和用户自有手机热点。
- 多网络采用“每次启动重新检测”的方式适配，不保存固定 IPv4；家庭 Wi-Fi 与手机热点可获得不同地址。
- 服务运行期间若网络或 IPv4 变化，终止当前会话并要求重新开启服务。
- 不支持在 `Public` 网络中启动文件传输服务。
- Windows 网络类别和防火墙配置只检测并提供设置入口，不由程序自动修改。
- 第一版不要求安装程序，先使用源码或便携版运行。
- 防火墙必须保持开启；正式方案不能依赖关闭防火墙。

### 3.2 不实现或当前不实现的内容

以下内容分为两类：`Public` 网络支持属于明确不实现的产品边界；其余项目在当前版本不实现，除非后续需求发生变化。

- **不实现：在 Windows `Public` 网络中提供文件传输服务。**
- 公网访问和端口映射。
- 手机 MAC 地址鉴权。
- 面向陌生网络的完整 HTTPS 证书与信任体系。
- Windows、Android 原生双端应用。
- 多用户账号系统。
- 高并发传输。
- 云端中转。
- 自动更新。
- 安装和卸载程序。

### 3.3 为什么不开发 Public 网络模式

`Public` 网络不是简单地在现有服务上增加一个“允许公用网络”开关。若要在咖啡店、酒店、机场、公司访客网络等陌生局域网中可靠传输文件，至少会引入以下额外成本：

- **客户端认证**：同一网络中可能存在未知设备，必须可靠区分已信任客户端与陌生客户端，不能依赖 IP 或随机 MAC。
- **传输加密**：普通 HTTP 会暴露文件内容和访问凭据；面向不可信网络需要 TLS/HTTPS 或等价的安全传输机制。
- **证书信任**：局域网 IP 很难直接获得浏览器天然信任的证书。自签名证书虽然能加密链路，但浏览器无法天然确认服务器身份；若建立自有 CA、安装证书或引入域名，会显著增加部署和维护成本。
- **中间人、窃听与重放风险**：仅增加配对码或 Cookie 不能自动解决不可信网络中的中间人攻击、凭据窃取和重放问题。
- **网络环境差异**：公共 Wi-Fi 可能启用客户端隔离、访客网络策略、端口限制、企业组策略或第三方安全软件，程序无法保证设备间能够直接通信。
- **测试矩阵扩大**：需要额外覆盖酒店/咖啡店/公司网络、不同路由器隔离策略、证书异常、认证失败、HTTPS 浏览器兼容等大量场景。
- **长期维护成本**：一旦宣称支持 Public 网络，就需要长期维护认证、加密、证书、兼容性和安全问题，这与本项目“临时、轻量、个人使用优先”的目标不符。

因此，本项目明确不开发 `Public` 网络传输能力。外出使用时，优先建议使用用户自己的手机热点，并将该连接在 Windows 中作为可信 `Private` 网络使用。程序仍会识别 `Public` 网络，以便说明为什么不能启动服务并提供 Windows 设置入口；这属于诊断功能，不代表支持 Public 网络。

### 3.4 HTTP 服务实现边界

- 第一阶段以 `python -m http.server` 或标准库等价实现作为轻量原型，验证 LAN 链路、地址展示、监听状态和基本下载。
- 从第二阶段起，正式 HTTP 应用层采用 **Bottle** 作为首选实现。
- 选择 Bottle 的主要原因：
  - 单文件框架，整体足够轻量；
  - 无额外第三方依赖链，便于源码运行和后续便携打包；
  - 原生提供路由、请求/响应封装、Cookie、文件上传和静态文件服务；
  - 能显著降低手写 `http.server` Handler 时对 multipart、Cookie、URL 分派和路径安全的维护成本；
  - 能力与本项目“Private LAN + 浏览器客户端 + 临时服务 + 少量接口”的规模匹配，不需要引入 Flask/FastAPI 的更大功能面。
- `python -m http.server` 继续保留为网络基线、故障排查和只读原型工具，不作为最终双向传输实现。
- 若后续需求明显超出 Bottle 能力，再单独重新评估更完整的框架；当前不提前为理论扩展预留大型 Web 架构。

### 3.5 客户端信任模型（已实现）

Private 网络不能替代客户端身份识别，但本项目也不采用 IP 或 MAC 作为长期设备身份。当前采用“配对一次、后续自动识别”的轻量模型：

- 手机端继续使用浏览器，不开发专用 Android App。二维码只是把浏览器带到当前服务 URL 或一次性配对 URL。
- 第一次由用户完成配对/确认；成功后浏览器保存高熵随机凭据，PC 端保存相应凭据哈希或等价不可逆记录。
- 后续再次访问时浏览器自动携带凭据，不要求用户反复输入配对码。
- DHCP 地址、SSID、随机 MAC 和当前 IP 不作为长期客户端身份。
- 用户可以在 PC 端取消信任；浏览器清除站点数据、无痕模式或重装浏览器后需要重新配对。
- 该模型只面向可信 `Private` 网络，不宣称达到陌生 Public 网络下的认证与抗窃听安全等级。

### 3.6 尚未最终确定的技术选择

## 4. 需要逐步理解的五个通信概念

| 概念 | 当前阶段够用的理解 |
| --- | --- |
| IP 地址 | 电脑在当前局域网中的门牌号，例如 `192.168.1.35` |
| 端口 | 某个程序使用的网络入口，例如 `8765` |
| 监听 | 程序打开端口并等待其他设备访问 |
| HTTP 请求 | 手机浏览器向电脑请求网页或文件 |
| 防火墙 | 决定外部设备是否允许进入这个端口 |

暂时不要求系统学习 TCP、路由、DNS、TLS、子网划分等完整理论。实际遇到相关问题时再补充对应知识。

## 5. 总体阶段规划

| 阶段 | 名称 | 核心目标 | 阶段结束时得到什么 |
| --- | --- | --- | --- |
| 第一阶段 | 家庭网络只读下载原型 | 打通“电脑共享、手机下载”的最小链路 | 一个可手动启动、停止的 Python 下载服务器 |
| 第二阶段 | 安全上传与文件处理 | 允许手机上传文件，同时控制路径、文件名和失败文件 | 可双向传输的命令行版本 |
| 第三阶段 | 桌面 GUI | 用界面完成目录选择、启停、地址展示和基本状态显示 | 可视化桌面版本 |
| 第四阶段 | 5 分钟生命周期 | 加入倒计时、到期策略、倒计时重置和传输宽限 | 可自动关闭端口的临时服务 |
| 第五阶段 | 托盘与 Windows 通知 | GUI 可隐藏到托盘，并通过通知操作服务 | 日常使用形态基本完成 |
| 第六阶段 | 网络与防火墙诊断 | 检测网卡、IP、Private/Public 和规则状态，并对 Public 明确阻止启动 | 能解释常见“手机无法访问”问题并提供系统设置入口 |
| 第七阶段 | 便携打包与稳定性测试 | 打包并在干净环境中验证 | 可在其他 Windows 电脑试用的便携版 |
| 第八阶段 | 安装和卸载（可选） | 管理固定路径、快捷方式和清理 | 面向其他用户分发的安装包 |

阶段顺序原则：前一阶段未达到验收标准，不进入下一阶段。个别界面草图可以提前制作，但不能代替核心功能验收。

## 6. 第一阶段：家庭网络只读下载原型

### 6.1 阶段目标

在可信家庭 Wi-Fi 中，由电脑启动一个只读文件服务器，Android 手机通过浏览器访问并下载指定目录内的文件。服务器可以手动关闭，且关闭后端口不再接受访问。

这一阶段不开发完整 GUI，不做上传，不自动修改网络类别或防火墙。若检测到 `Public` 网络，只记录并验证“拒绝启动 + 给出说明”的行为，不进行 Public 网络传输测试。

### 6.2 使用条件

- 电脑运行 Windows 11。
- 电脑与手机处于同一个可信局域网，优先使用家庭 Wi-Fi；也可以测试用户自有手机热点。
- Windows 将当前连接设置为 `Private`。
- Windows 防火墙保持开启。
- 当前 Python 环境可正常运行脚本。
- 测试时明确记录 Clash、VPN 或 TUN 是否开启。

### 6.2.1 已确认的开发机网络基线（2026-09-14）

当前已在“电脑连接用户自有手机热点”的环境下完成一轮基线检查：

- 当前实际 LAN 接口为 `WLAN`。
- 当前热点 IPv4：`10.118.84.152`。
- 子网掩码：`255.255.255.0`，即当前 IPv4 网段可按 `/24` 理解。
- IPv4 默认网关：`10.118.84.206`。
- 同时可见一个 IPv6 链路本地网关地址；首版仍只使用 IPv4，不把 IPv6 纳入地址展示和绑定策略。
- Windows 将当前热点连接识别为 `Private`。
- `Meta` 为当前代理软件使用的 TUN 虚拟适配器，不作为文件服务器 LAN 地址候选。
- `无线局域网适配器 本地连接* 1`、`本地连接* 2` 当前均为断开状态，不作为当前 LAN 接口；后续按 Wi-Fi Direct/虚拟接口处理。
- `以太网适配器 蓝牙网络连接` 不属于当前目标传输路径，默认排除。
- 当前代理/VPN 使用“规则（Rule）”模式。程序不控制代理模式，只把 TUN/VPN 作为诊断因素；局域网访问应由代理配置放行直连。
- 当前 Windows 防火墙界面可见：`Python HTTP 8000` 允许 `Private`；另有两个同名 `Python` 项，分别存在 `Private` 与 `Public` 勾选；`PowerShell` 同时允许 `Private/Public`。这些显示项尚未核对到具体 `python.exe` 路径、协议和端口，因此不能仅凭名称判断哪条规则实际控制当前服务器。
- 当前环境中已存在端口 `8000` 的 Private 放行记录；项目文档原先暂定默认端口仍为 `8765`。本次检查不自动改变默认端口，第一阶段正式实现前必须统一“程序端口、测试命令和防火墙检查对象”。

当前尚未完成的开发机侧核验：

1. 当前实际使用的 `python.exe` 路径，与防火墙中两个 `Python` 项分别对应哪个可执行文件。
2. 运行 `http.server` 时实际 `LocalAddress` 是 `0.0.0.0`、WLAN IPv4 还是其他地址。
3. 热点网段 `10.118.84.0/24` 的 Windows 本地路由是否明确落在 `WLAN`，以及 `Meta` TUN 对该网段是否存在异常捕获。
4. 家庭 Wi-Fi 在当前配置下尚未完成同一套基线复测。

有线 Ethernet 不列为首版开发机验收条件：当前笔记本没有原生 RJ45 端口，也没有必要为了首版专门建立有线测试环境。代码不应主动排斥 Ethernet，但首版正式验证以 Wi-Fi LAN 为主。

### 6.4 任务清单

#### 任务 1：记录并补齐开发环境基线

已完成的热点环境信息见 6.2.1。剩余工作只补齐对后续实现有直接价值的项目，不继续无限扩展系统调查范围。

仍需确认：

- Windows 版本。
- Python 版本及当前解释器路径。
- 当前活动网络名称和网络类别。
- 当前实际 LAN IPv4。
- 运行服务器时的实际监听地址。
- 当前 Python 防火墙规则究竟对应哪个 `python.exe`、哪个端口和哪个 Profile。
- WLAN 与 TUN/Meta 对当前 LAN 网段的路由关系。
- 第一阶段正式采用的统一端口（原计划暂定 `8765`，当前系统已有 `8000` 的 Private 规则，二者需择一并统一）。

建议使用的只读检查命令：

```powershell
python --version
Get-Command python | Select-Object -ExpandProperty Source
Get-NetConnectionProfile | Format-Table Name, InterfaceAlias, NetworkCategory, IPv4Connectivity
Get-NetIPAddress -AddressFamily IPv4
Get-NetRoute -AddressFamily IPv4
ipconfig
```

启动测试服务器后，再确认监听：

```powershell
Get-NetTCPConnection -LocalPort <实际端口> -State Listen |
    Format-Table LocalAddress, LocalPort, OwningProcess
```

核对 Python 相关防火墙规则：

```powershell
Get-NetFirewallRule -DisplayName "*Python*" |
    Format-Table DisplayName, Enabled, Profile, Direction, Action

Get-NetFirewallRule -DisplayName "*Python*" |
    Get-NetFirewallApplicationFilter |
    Format-Table Program

Get-NetFirewallRule -DisplayName "*Python*" |

```

完成标志：能够明确回答“当前服务器由哪个 `python.exe` 运行、监听在哪个本地地址、当前 LAN 网段走哪张物理网卡、对应防火墙规则是什么”。完成这些后停止继续收集低价值环境信息，进入实现阶段。

### 6.6 第一阶段故障排查顺序

如果手机无法访问，严格按顺序排查，不同时修改多个设置：

1. 服务器进程是否仍在运行。
2. 实际端口是否处于监听状态，且 `LocalAddress` 不是仅限 `127.0.0.1`。
3. 程序选择的是否是真实 `WLAN`/LAN IPv4，而不是 `Meta` TUN、Wi-Fi Direct、Bluetooth PAN 等接口。
4. 电脑能否访问 `127.0.0.1:<实际端口>`。
5. 电脑能否访问自己的局域网 IPv4 地址。
6. 手机和电脑是否处于同一可互通的局域网。
7. 当前网络是否为 `Private`。
8. 防火墙规则是否确实对应当前 `python.exe` 或当前端口，而不是名称相似的旧规则。
9. 手机与电脑的 Clash/VPN/TUN 是否干扰局域网地址；Rule 模式异常时可临时用 Direct/关闭 TUN 交叉验证。
10. 路由器/热点是否启用了访客网络、AP Isolation 或客户端隔离。
11. 是否存在第三方防火墙或终端安全软件额外阻止入站连接。

关闭全部防火墙只能用于短暂定位，不能作为最终解决方案。验证完成后必须重新开启。

## 7. 后续阶段的初步边界

### 第二阶段：安全上传与文件处理

从本阶段开始，正式 HTTP 应用层切换为 **Bottle**。Bottle 负责路由、浏览器文件上传、Cookie 读写和静态/下载响应；文件路径校验、`.part`、同名策略、磁盘空间检查和流式写入仍由项目自身的文件处理模块负责。

重点处理固定接收目录、文件名清理、同名文件、临时 `.part` 文件、大小限制、磁盘空间和流式上传。完成后形成可双向传输的命令行版本。

当双向传输链路稳定后，再加入轻量的“首次配对—长期信任”机制：首次由用户确认，后续浏览器凭据自动识别可信客户端；不使用 IP/MAC 白名单，不要求每次重新认证。该认证只面向 Private 网络，浏览器凭据由 Bottle 的 Cookie 能力承载，PC 端保存相应凭据哈希或等价不可逆记录。

### 第三阶段：桌面 GUI

使用 pywebview 建立控制窗口，将服务器逻辑与界面逻辑分离。界面负责选择目录、启停服务、显示地址与状态，不直接承担文件传输。

实施状态（2026-09-15）：已完成并通过人工验收。桌面入口为 `desktop.py`；控制窗口支持原生目录选择、上传上限设置、非阻塞启停、访问地址、网络接口和配对码显示，以及使用系统浏览器打开传输页。文件传输仍由 Bottle 应用处理。服务控制器具备重复启动保护和线程安全的幂等关闭；在第三、四阶段，GUI 停止服务或直接关闭窗口后，TCP 8000 均已验证释放。该“关闭窗口即停止”语义是阶段历史行为，已在第五阶段替换为隐藏到托盘。命令行入口 `app.py` 保持兼容。

### 第四阶段：5 分钟生命周期

使用会话 ID 和单一截止时间管理倒计时。到期后拒绝新传输，并为已经开始的传输提供有限宽限。旧计时器和旧通知不得控制新会话。

实施约定（2026-09-16）：默认会话 5 分钟；点击“重置为 5 分钟”会从点击时重新计算完整 5 分钟，而不是在原截止时间上累加；剩余 60 秒进入醒目提示。截止时间在监听器准备完成后开始计算，避免初始化耗时侵占可用时间。到期立即拒绝新请求，已开始的上传和下载最多宽限 60 秒。手动停止立即生效。检测到睡眠恢复后终止会话，不暂停倒计时。配对码对每台新设备单次有效，配对成功后原子轮换；已有可信客户端不消耗配对码。传输量与速率使用十进制 `MB / MB/s`。同一次文件下载的并行 HTTP Range 请求按逻辑任务和字节区间聚合，文件任务与请求流分别计数，重叠字节不重复计入主传输量。服务停止原因与传输失败原因分别统计，并写入不包含路径、配对码或凭据的本地轮转日志。

正式设备管理由 PC 控制窗口负责，可列出并撤销单个或全部可信浏览器；手机端仍可自助取消自身信任。文件链接先进入手机状态页，再在隐藏下载目标中启动附件响应。连接中断后状态页保留明确提示；服务重新启动且文件未变化时，服务器支持标准 HTTP Range 请求，浏览器是否自动继续由具体下载管理器决定。

### 第五阶段：托盘与 Windows 通知

关闭 GUI 只隐藏窗口；退出应用才终止托盘进程。通知提供“重置为 5 分钟”“立即关闭”和“打开窗口”。主程序保持普通权限运行。

实施状态（2026-09-17）：已完成并通过人工与自动化验收。`pystray` 提供最小托盘入口，`Windows-Toasts` 提供到期提醒和自动关闭通知，`ActionCoordinator` 统一承接 GUI、托盘与 Toast 动作，`ServiceController` 仍是服务状态的唯一权威。活动传输中点击 X 后窗口隐藏、传输继续且 TCP 8000 保持监听；同一窗口连续恢复 20 次未丢失状态。托盘重置、停止、退出，Toast 重置、停止、打开窗口，旧 revision/session 隔离，通知清理失败兜底，托盘初始化失败保护及异常退出遗留通知清理均已通过。最终 Private 热点实测启动约 `0.396s`、停止约 `0.173s`；第五阶段收官时共有 43 项自动化测试。

已知非阻塞系统行为：Windows 已展开的托盘菜单不会在后台状态变化时原地重绘，收起后重新打开即可读取最新状态；Windows 前台保护下窗口激活只保证尽力而为，但窗口可靠可见和状态不丢失已经通过验收。源码开发机已注册自定义 AUMID `LanDrop.Desktop`；后续便携打包与安装阶段必须验证目标机上的 AUMID、快捷方式和通知身份注册策略。

#### 第五阶段冻结方案（2026-09-16）

第五阶段的技术选型和职责边界在正式编码前冻结。托盘的核心任务仅是：在主窗口隐藏后仍可找回窗口，并控制已经运行的服务。它是 GUI 的一个入口，不是第二个 GUI；不实现复杂自定义托盘界面、独立配置页、文件浏览器或第二套状态/计时界面。

组件职责固定如下：

```text
pywebview Window（从程序启动存活到应用退出）
  └─ 主控制窗口：目录、可信设备、启停与完整状态

pystray Tray
  └─ 托盘图标和简洁菜单

Windows-Toasts
  └─ Toast 投递和按钮动作入口

ActionCoordinator
  ├─ 统一接收 GUI、托盘和 Toast 动作
  ├─ 调度窗口显示/恢复
  └─ 调用 ServiceController 的公开动作

ServiceController（service.py）
  └─ 服务、会话、截止时间、端口与传输生命周期的唯一权威控制器
```

- `pystray` 只负责 Windows 托盘；不因托盘引入 `pywin32`。若先行验证发现 `show()/restore()` 后的前台激活需要补充，只允许通过 pywebview 当前 Windows 原生后端做最小“尽力激活”，不得因此新增第二套窗口控制体系。
- `pywebview` 继续负责唯一主窗口。窗口从应用启动一直存活到应用退出；点击 X 时只隐藏，不销毁并重建 Window。
- `service.py` 中的 `ServiceController` 继续是启停、会话、截止时间、端口和传输生命周期的唯一权威控制器。第五阶段新增 `landrop/tray.py` 作为托盘适配器，并新增统一动作协调层；二者不得复制服务状态机。
- `Windows-Toasts` 独立负责 Windows Toast。交互 Toast 固定使用自定义 AUMID `LanDrop.Desktop`；本项目只保证 LanDrop 进程仍存活时通知中心按钮能回送到当前进程，不实现“进程退出后由旧通知重新启动应用”。应用启动时清理可能由异常退出遗留的 LanDrop 可操作 Toast，正常退出时再次清理当前可操作 Toast。
- 托盘和 Toast 都不直接接触 Bottle、WSGI、socket 或计时器；它们只能调用统一协调层。pystray 与 Windows-Toasts 的回调线程不得直接操作 pywebview Window，所有窗口显示、恢复和激活动作必须经统一 GUI 调度路径执行。

##### 托盘菜单与窗口语义

第五阶段正式托盘菜单保持最小化：

```text
打开窗口
────────────
状态：运行中 / 已停止        （只读）
重置为 5 分钟               （仅服务运行时启用）
停止服务                     （仅服务运行时启用）
────────────
退出 LanDrop
```

托盘不提供“启动服务”、目录选择、可信设备管理或实时逐秒倒计时；启动服务及完整配置仍回到主窗口完成。服务状态变化时才刷新托盘菜单，不为秒级倒计时每秒更新菜单。

在托盘已确认可用 (`tray_ready`) 时，窗口关闭语义为：

```text
活动传输 → 点击 X → pywebview 窗口隐藏 → 服务继续运行
         → 传输继续 → TCP 8000 继续监听

服务已停止 → 点击 X → 窗口隐藏 → 托盘进程继续等待下一次使用
```

若托盘初始化失败或运行中失效，不允许把主窗口隐藏成无法找回的后台进程。无托盘降级语义固定为：禁用“关闭到托盘”；点击 X 时直接通过统一 `request_exit(reason="app_exit")` 安全退出，并在能够显示状态时提示“托盘不可用，关闭窗口将退出 LanDrop”。不得产生不可找回的隐藏进程。

窗口重新打开时优先使用 `show()`/`restore()`；只有先行技术验证确认焦点不可靠时，才加入最小 Windows 原生“尽力激活”补充。硬性验收是窗口可靠重新可见且状态不丢失；Windows 前台焦点保护导致的偶发未抢到焦点不视为服务失败。

##### Toast 状态安全与生命周期

`ServiceController` 维护当前 `session_id` 和 `deadline_revision`：每次启动服务生成新的 `session_id`；同一服务会话中每次重置截止时间都递增 `deadline_revision`。

修改服务状态的 Toast 动作必须携带创建通知时的 `session_id + deadline_revision`。`reset` 与 `stop` 的“校验当前 session/revision + 执行动作”必须在 `ServiceController` 的同一锁/同一原子控制路径中完成，禁止先校验、后另行调用造成竞态。旧会话或旧 revision 的动作一律安全忽略。

“打开窗口”属于无状态 UI 动作，不修改当前服务，因此不因旧 `session_id/revision` 被拒绝；它只请求显示当前 LanDrop 窗口。

每个 `session_id + deadline_revision` 最多发送一次“即将到期”可操作 Toast。默认正式会话在剩余 60 秒时触发。Toast 使用固定 LanDrop 通知组，并以 `session_id + deadline_revision` 生成可唯一定位的 tag，便于替换和清理。发生重置、停止、会话到期、启动新会话或应用退出时，主动移除已经失效的可操作 Toast；应用启动时也清理异常退出可能遗留的旧可操作 Toast。主动清理只用于保持通知中心整洁，`session_id/revision` 原子校验仍作为最终安全兜底。GUI、托盘和 Toast 发起的普通“停止服务”统一沿用 `manual_stop`；只有应用整体退出使用 `app_exit`。

##### 统一退出

托盘“退出 LanDrop”是正常用户退出入口，但清理逻辑不得写死在托盘模块。所有合法退出路径统一调用 `request_exit(reason=...)`：

```text
标记应用进入 exiting
→ 使后续旧 Toast 状态修改动作失效
→ 通过 ServiceController 停止当前服务和活动传输
→ 清理当前可操作 Toast
→ 停止 pystray
→ 销毁 pywebview Window
→ 退出进程
```

正常用户退出的会话停止原因使用 `app_exit`。第四阶段的 `window_closed` 停止原因和相关验收仅代表第五阶段前的历史行为；第五阶段起点击 X 不再产生该停止原因。单实例/重复启动处理不属于第五阶段阻塞项，留到后续稳定性与打包阶段处理。

### 第六阶段：网络与防火墙诊断

显示当前物理 LAN 网卡、IPv4、网络类别、防火墙配置文件和规则状态，并识别常见 TUN/VPN/虚拟接口。程序只读检测系统状态并提供 Windows 官方设置入口，不自动修改网络类别、防火墙规则或代理/VPN 配置。

服务运行期间检测到活动 LAN、Wi-Fi 或 IPv4 变化时，终止当前传输会话并提示重新开启，不尝试把现有服务器热迁移到新接口。

若当前连接为 `Public`：

- 明确显示“当前网络不受本工具支持”。
- 不启动文件传输监听。
- 说明 Public 网络涉及额外的认证、TLS/证书信任和陌生同网设备风险。
- 提供 Windows 网络设置入口，供用户自行判断该网络是否应改为 `Private`。
- 对外出场景优先建议使用用户自有手机热点。

### 第七阶段：便携打包与稳定性测试

优先评估 PyInstaller `--onedir`。在另一台 Windows 电脑或干净测试环境中验证资源加载、通知、托盘、程序路径、网络检测和防火墙诊断行为。

### 第八阶段：安装和卸载（可选）

只有在需要稳定安装路径、快捷方式或对外分发时才加入。安装程序不得静默改变 Windows 网络类别；防火墙规则是否由安装器辅助创建，需要单独评估，并应明确展示给用户。优先考虑成熟安装器，不自行开发安装系统。
