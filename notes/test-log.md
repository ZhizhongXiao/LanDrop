### P6-D01：网络与防火墙诊断、Ethernet 与性能基准

- 日期：2026-09-17
- 状态：方案已冻结，待技术验证与正式实现。
- 启动检测：每次启动服务执行一次完整网络检测，并以 `InterfaceIndex + bound IPv4 + NetworkCategory` 作为本次进程内 session 的权威网络基线；接口别名只用于显示，服务重启后重新检测。
- 运行期检测：不做动态调频；新增独立 endpoint checker，优先复用 `_read_ipv4_table()`，不得直接复用会启动 PowerShell 的完整 `discover_interfaces()`。采用固定低频轻量匹配，具体周期通过 `2s / 3s / 5s` 候选实测后确定。

- 防火墙：采用异步深度诊断或短超时，不进入同步启动硬路径；未完成显示“检测中”，失败/权限不足显示“无法确定”，未发现明确 TCP 8000 allow 只提示“需检查/可能允许”，不阻止已经确认的 Private endpoint 启动。正式诊断不只按规则名称含 `Python` 筛选，继续只读检测，不自动改网络类别、防火墙规则、代理、VPN 或静态 IP。

- TUN/VPN：中性展示检测结果，存在本身不视为异常；可以提供 Windows 代理设置入口。
- Ethernet：正式加入无 WAN 路由器纯 LAN、两台 Windows PC 使用 RFC1918 静态地址（例如 `192.168.50.1/24` 与 `192.168.50.2/24`）且由用户确认两端为 Private 的网线直连、WLAN+Ethernet 共存测试；保留 Public 拒绝启动反向测试，不依赖 `169.254.0.0/16` link-local。用户已做过路由器组网和 PC 直连手动 IP 的先行实验，至少一台接口状态正常的 PC 可稳定发包。

- 浏览器上传统计缺陷与修复：初次上传十进制 1 GB 文件时，页面约等待 10 秒后直接成功，GUI 错误显示约 `300–450 MB/s`。根因是读取 multipart 表单中的 CSRF/文件字段会先触发 Bottle 完整解析请求体，LanDrop 随后才开始生命周期计时并把 Bottle 临时文件复制到接收目录，因此统计成了本地临时文件复制速度，而非网络上传速度。主浏览器路径现改为 XHR 原始文件流 `/upload/raw`，在读取 WSGI 输入流前建立上传任务，并在页面显示上传百分比、十进制 MB 和客户端实时 MB/s；原 multipart `/upload` 仅保留为无脚本兼容回退。

- 性能推论边界：`948 Mbit/s` 对 `699–705 Mbit/s` 的底层方向差异尚未精确归因到某一台电脑或具体网卡选项；当前只可将范围缩小到网卡发送/接收路径、驱动、卸载/流控能力或 Windows 网络栈。SMB 双向约 `87.65 / 88.77 MB/s` 表明其协议/存储路径会掩盖较快方向，但不能推翻 iperf3 的方向基线。第六阶段不为此修改系统高级网络设置；进一步交换角色或引入第三端属于可选硬件诊断。
